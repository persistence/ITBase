# 整体架构

一个部署是一个组织，下面有多个应用。CRM、OA 跑在同一套内核上。应用做二次开发，不另建用户、权限和数据写入。

本文是总图。字段、表和接口写在 [内核](内核/) 各模块文档里。应用的验收标准写在 `docs/应用/{appCode}/`。实现栈是 Go、GoFrame、MySQL 8、cel-go、Yaegi。管理端与内核一起发布，用户端按应用构建。

用户与组织、数据模型、工作流、权限已经成文。「应用内模块」对源码修订的改法，先以本文为准，再写入对应文档。

## 总图

```text
管理端（系统自带，登录后的壳）
用户端 client（每个应用一份，依赖内核组件包）
        │
        ├─ 内核 HTTP：/api/v1/org  /api/v1/model  /api/v1/data  /api/v1/ext-src
        └─ 扩展 HTTP：/api/v1/ext/{appCode}/{moduleCode}/…
                │
        宿主进程（api 或 worker）
        ├─ 用户与组织
        ├─ 数据模型
        ├─ 权限
        └─ 工作流
                │
        每个已发布模块一个 Yaegi 池
                │
        MySQL：目录、组织表、业务表、变更历史、按模块存放的源码修订
```

内核模块内部是 `api` → `controller` → `service`。模块之间只经 service 调用。应用代码不进入这三层。宿主用该模块已发布修订的路由表匹配扩展请求。

前端组件随内核版本发布，是 client 构建时依赖的包。它不是宿主里的模块。文件和通知以后另立内核模块。

## 内核

| 模块 | 文档 | 拥有 |
|---|---|---|
| 用户与组织 | [用户与组织](内核/用户与组织/README.md) | 人、部门、任职、职位、组织角色、登录方式、会话 |
| 数据模型 | [数据模型](内核/数据模型/README.md) | 目录、物理表、CEL、数据读写、变更历史、模块源码与解释器 |
| 权限 | [权限](内核/权限/README.md) | 范围谓词。负责人、团队、临时共享和动作许可随后仍写在本模块 |
| 工作流 | [工作流](内核/工作流/README.md) | 流程定义、实例、待办、办理人。审批流是其中的人工节点 |

用户与组织拥有 `org_*`。用户 id 就是 `created_by`、`updated_by` 和变更历史里的 `actor_id`。`0` 只表示没有登录用户的系统调用，不是合法用户 id。管理写接口只认 `platform_admin`，不回调权限模块。本模块不保存数据范围，也不配置流程节点。

登录留在本模块，不另立内核模块。实现文档是 [会话](内核/用户与组织/04-会话.md) 和 [登录方式](内核/用户与组织/05-登录方式.md)。管道是：验证凭据，解析出唯一的 `org_user`，状态必须是 `active`，然后签发同一份会话。管理端和各应用 client 携带这份会话。第一期只有登录名和口令。企业接入时增加 OIDC 授权码，以及企业微信、钉钉两个适配器。其后是 LDAP 或 AD 的口令绑定，以及 TOTP 第二因素。个人微信、短信验证码和邮件链接不进入内核。

数据模型内部按七个实现模块落地：元数据目录、结构同步、规则校验、数据读写、变更历史、源码与发布、解释器运行时。全文索引挂在目录、结构同步和数据读写上。多实例归属是部署约束。解释器只拿到 `itbase.dev/itb`，唯一数据端口是数据读写，因此源码和解释器留在数据模型里。写入只使用 `active` 的字段和关联，并经过规则校验和权限挂点。CEL 只做单行布尔规则。跨多行写入、循环汇总和自定义响应形状写领域函数。

权限模块把部门闭包和角色绑定编译成谓词，规则见 [权限](内核/权限/README.md)。数据 API 只接收已解析的谓词，组织模块不生成 SQL。负责人、团队、按条件共享、临时授权和动作许可仍属于本模块，放在第一期谓词之后。动作许可落地前，领域函数自行读取主体事实，再决定能否执行确认、作废这类动作。

工作流的办理人引用用户 id、主部门或 `dept_leader`。人工办理在 `api` 进程调用已发布领域函数。超时和变更驱动的推进在 `worker` 进程调用同一个函数。两条路都走宿主的模块调用入口。`/api/v1/domain/{appCode}/{funcName}` 不挂到公网。工作流不另备脚本语言，也不打开第二个解释器。

页面、工作流和权限只引用已经 `active` 的 `entityCode`、`fieldCode`、`linkCode`，不写入数据模型目录。审批流是工作流定义里的人工节点，不单建目录。

## 应用内模块

应用是数据和权限的边界。模块是该应用内的源码、路由和发布边界。客户和商机放在同一应用的不同模块里，不拆成两个应用。

- 实体、选项集和 CEL 登记在应用上，目录不设 `module_id`。同一 `appCode` 下的实体可以互相关联。一个实体编码在应用内只登记一次，由一个模块的 spec 描述。
- `moduleCode` 与 `appCode` 使用同一套编码。每个模块有自己的领域包、接口包、草稿和已发布修订。上限按模块计算：源码合计 512KB，最多 32 个文件、32 条路由。
- 一个已发布模块对应一个解释器池。包路径是 `itbase.app/{appCode}/{moduleCode}/domain` 和 `itbase.app/{appCode}/{moduleCode}/api`。接口包可以 import 本模块的领域包。领域包不 import 接口包，也不 import 其他模块。
- 跨模块调用经宿主按模块编码和函数名进入对方已发布的池。工作流使用这个入口。
- 扩展路由是 `/api/v1/ext/{appCode}/{moduleCode}/…`。同一应用内，方法加路径模板跨模块也不可重复。路由不得覆盖 `/api/v1/model` 和 `/api/v1/data`。
- 收紧列时，按引用该列的模块修订检查心跳。
- 跨应用只引用内核登记的系统实体，现在是 `org` 下的 `user` 和 `department`。

## 规格、源码与运行副本

先写 spec，再写代码或配置。内核 spec 不写客户、商机、请假单这类业务对象。

| 位置 | 内容 |
|---|---|
| `docs/内核/{模块}/` | 四个内核模块。阅读顺序与落地顺序相同 |
| `docs/内核/前端组件/` | 组件的类型、属性和事件 |
| `docs/应用/{appCode}/README.md` | 应用的能力、模块清单和完成标准 |
| `docs/应用/{appCode}/{moduleCode}/01-实体.md` | 本模块负责登记的实体、字段、关联、索引 |
| `docs/应用/{appCode}/{moduleCode}/02-规则.md` | 这些实体上的 CEL，标明 `local` 或 `server` |
| `docs/应用/{appCode}/{moduleCode}/03-页面.md` | 屏幕、组件、绑定的编码和路由 |
| `docs/应用/{appCode}/{moduleCode}/04-动作.md` | 领域函数、扩展路由、入参和完成标准 |

三份事实分工如下。环境之间导出模块修订包做晋升，不在生产库里改草稿。

| 份 | 位置 | 职责 |
|---|---|---|
| spec | `docs/应用/{appCode}/` | 验收标准 |
| 编辑面 | 下面的 `apps/` 目录 | 唯一编辑来源 |
| 运行副本 | 该环境中 `phase = published` 的模块修订，以及已构建的 client | 该环境正在服务的版本 |

```text
apps/{appCode}/{moduleCode}/domain/*.go
apps/{appCode}/{moduleCode}/api/*.go
apps/{appCode}/{moduleCode}/routes.json
apps/{appCode}/client/
```

`domain`、`api` 和 `routes.json` 推到该模块草稿，带 `baseEditVersion`，再执行 `:check`。检查失败时返回文件名和行号，运行池不变。版本不一致时停止推送，重新读取草稿。`client/` 按各模块的 `03-页面.md` 编写，使用内核组件包。它不进入 `dm_file`，也不由 Yaegi 解释。

发布成功是该模块草稿在一个事务里变为 `published`，原已发布修订变为 `retired`。失败时原修订继续服务。`api` 和 `worker` 从库中的已发布修订装入虚拟文件系统并建池，不从磁盘加载。查看某次修订时，按模块和 `revision` 导出到临时目录，只读，不参与装载。

能用 CEL、页面和流程定义表达的逻辑留在 spec 里。领域函数只写跨行事务和自定义响应。

## 前端

管理端是登录后的壳，屏幕在平台仓库里。它提供登录、应用入口，以及组织、目录、权限、工作流和模块发布。管理端可以查看草稿并发起检查和发布，不与 `apps/` 并行编辑草稿。

每个应用一份 client，构建时固定内核组件包的版本。壳按 `appCode` 加载已构建的资源。client 调用数据 API 和已发布扩展路由，不调用结构 API 和发布 API。

第一批组件是：按逻辑类型的输入（文本、数值、日期、选项、用户引用、部门引用），绑定数据 API 的列表、表单、详情和导航，提交前执行 `local` CEL，以及调用已发布路由的动作按钮。文件输入随文件模块进入组件包。待办和办理组件随工作流进入组件包。实体设计、组织树和源码发布由管理端自己写。

## 接口

| 前缀 | 读者 | 作用 |
|---|---|---|
| `/api/v1/org` | 管理端写；已登录用户读自己的资料、部门和任职 | 用户、部门、职位、角色、口令校验、会话 |
| `/api/v1/model` | 管理端 | 目录与结构。请求带应用标识 |
| `/api/v1/data` | 用户端、解释器、工作流 | 业务记录读写 |
| `/api/v1/ext-src` | 管理端 | 按模块保存草稿、检查、发布 |
| `/api/v1/ext/{appCode}/{moduleCode}/…` | 已登录用户 | 该模块已发布的扩展路由 |

扩展路由只要求已登录。行级权限在 `itb.App` 的读写上。权限和工作流的路径在各自模块文档里定义。

## 进程

同一份二进制按角色启动。生产不用 `all`。

| 角色 | HTTP | 解释器池 | 修订轮询 | 变更消费 |
|---|---|---|---|---|
| `api` | 对外 | 每个已发布模块一个池 | 有，并写心跳 | 无 |
| `worker` | 不对外 | 每个已发布模块一个池 | 有，并写心跳 | 有。先抢租约，同一消费者同一时刻只有一个 leader |
| `all` | 仅本地全开 | 有 | 有 | 有，仍抢租约 |

`worker` 调用领域函数时：

- 处理变更时沿用该变更的 `actor_id`。定时催办使用 `0`。权限挂点把 `0` 识别为系统调用，只放行工作流和消费端发起的写入。
- 这次调用产生的写入带上来源序号。消费端不再把这些写入派发回同一个领域函数。
- 解释器卡死只影响本进程上的领域调用。`worker` 的池故障不导致 `api` 拒绝 `/api/v1/data`。

## 当前范围

现在这套分层能支撑的骨架是：同一应用内的实体和主从写入、单行 CEL、按部门和角色绑定形成的范围谓词、审批，以及按模块发布的自定义动作。

| 能力 | 落点 |
|---|---|
| 汇总与报表 | 数据模型的聚合查询。列表仍只查当前实体，每页最多 200 行 |
| 负责人、团队、按条件共享、临时授权、动作许可 | 权限 |
| 会签、加签、转办、撤回、退回、代理人 | 工作流 |
| 看板、向导、日历、公文套红 | 该应用的 client |
| 状态变更后的自动动作、超时催办 | `worker` 调用已发布领域函数 |
| 批量导入、待办推送、文件 | 以后的文件模块和通知模块。外部身份沿用用户模块已留的位置 |
| 集团多法人、多账套 | 超出一个部署一个组织，不在本方案里 |

## 落地顺序

1. 数据模型、用户与组织，完成标准见各自 README。第一期只开通口令登录和会话。
2. 源码、解释器和多实例改为按模块修订。`api` 与 `worker` 都为已发布模块建池。改 [源码与发布](内核/数据模型/06-源码与发布.md)、[解释器运行时](内核/数据模型/07-解释器运行时.md) 和 [多实例归属](内核/数据模型/08-多实例归属.md)。
3. 权限的第一期谓词。完成标准见 [权限](内核/权限/README.md)。解释器读写走同一挂点。
4. 组件包和管理端。壳能登录并进入应用。管理端能维护结构和组织。组件能绑定目录并执行 `local` CEL。
5. 一个样例应用、一个模块。登记实体，配页面，发布一个跨行动作。用户端能录入。规则失败时整单回滚。发布失败时旧修订继续服务。
6. 工作流。完成标准见 [工作流](内核/工作流/README.md)。人工办理和 `worker` 上的自动推进都调用已发布领域函数，并遵守来源序号规则。
7. 按产品需要补聚合、共享、动作许可、文件和通知。

第 5 步之前，不把复杂 CRM 或 OA 的业务规则写进 Yaegi。
