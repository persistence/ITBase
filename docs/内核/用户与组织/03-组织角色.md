# 组织角色

职责：把用户分成稳定的组，供管理门禁、权限模块和流程引用。第一期有两类系统角色，管理员也可以新增自定义角色。

不负责：实体、字段和数据范围的策略；流程节点的办理人表达式。这两处只读取本模块给出的事实。职位到角色的自动授予第一期不做，避免改职位名称就改变权限。

依赖：[用户](01-用户.md) 提供用户 id 和状态；[部门与职位](02-部门与职位.md) 提供部门 id、任职和闭包。

接口前缀 `/api/v1/org`。角色和绑定的写操作要求 `platform_admin`。已登录用户可以读取角色名录，以及自己的绑定和自己的主体事实。

## 1. 角色

```sql
CREATE TABLE org_role (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '角色主键',
  code          VARCHAR(40)     NOT NULL COMMENT '角色编码。创建后不改',
  title         VARCHAR(80)     NOT NULL COMMENT '显示名',
  scope         VARCHAR(16)     NOT NULL COMMENT 'org 组织范围，dept 部门范围',
  kind          VARCHAR(16)     NOT NULL COMMENT 'system 系统角色，custom 自定义角色',
  status        VARCHAR(16)     NOT NULL COMMENT 'active、disabled',
  row_version   BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '乐观锁',
  created_at    DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  created_by    BIGINT UNSIGNED NOT NULL COMMENT '创建人用户 id。初始化的系统角色写 0',
  updated_at    DATETIME(3)     NOT NULL COMMENT '最后修改时间，UTC',
  updated_by    BIGINT UNSIGNED NOT NULL COMMENT '最后修改人用户 id',
  PRIMARY KEY (id),
  UNIQUE KEY uk_org_role_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '组织角色';
```

`scope` 在创建时确定，之后不改。

| 编码 | kind | scope | 含义 |
|---|---|---|---|
| `platform_admin` | `system` | `org` | 管理用户、部门、职位和角色 |
| `dept_leader` | `system` | `dept` | 某个部门的负责人。一个部门可以有多名 |

系统角色由初始化写入。它们的编码、`scope`、`kind`、`status` 都不能改，显示名可以改。自定义角色的 `kind` 固定为 `custom`，可以停用后再启用。停用后，主体事实不再返回它的绑定；绑定行本身保留。不提供删除角色。

普通成员不是角色。有效用户不需要一人一行的「成员」绑定。

## 2. 绑定

```sql
CREATE TABLE org_role_binding (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '绑定主键',
  role_id       BIGINT UNSIGNED NOT NULL COMMENT 'org_role.id',
  user_id       BIGINT UNSIGNED NOT NULL COMMENT 'org_user.id',
  dept_id       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '部门范围角色的部门 id。组织范围角色固定为 0',
  open_token    BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '未结束为 0。结束后写成该行 id',
  started_at    DATETIME(3)     NOT NULL COMMENT '开始时间，UTC',
  ended_at      DATETIME(3)     NULL COMMENT '结束时间，UTC。未结束为空',
  row_version   BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '乐观锁',
  created_at    DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  created_by    BIGINT UNSIGNED NOT NULL COMMENT '创建人用户 id',
  updated_at    DATETIME(3)     NOT NULL COMMENT '最后修改时间，UTC',
  updated_by    BIGINT UNSIGNED NOT NULL COMMENT '最后修改人用户 id',
  PRIMARY KEY (id),
  UNIQUE KEY uk_org_role_binding_open (role_id, user_id, dept_id, open_token),
  KEY idx_org_role_binding_user (user_id, open_token),
  KEY idx_org_role_binding_dept (dept_id, role_id, open_token)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '角色绑定';
```

`dept_id = 0` 表示这条绑定覆盖整个组织。组织范围的角色必须写 `0`。部门范围的角色必须写一个真实部门 id，且该部门为 `active`。

新建绑定要求用户状态为 `active`，角色状态为 `active`。同一角色、同一用户、同一 `dept_id` 只能有一条未结束绑定。

结束绑定时写下 `ended_at`，并把 `open_token` 写成该行 id。用户离职时，用户模块在同一事务里结束他的全部未结束绑定。用户只是停用时不结束绑定。

本模块的管理接口判断 `platform_admin` 时，只看未结束绑定，并且用户自己的状态是 `active`。最后一名 `active` 用户的 `platform_admin` 绑定拒绝结束，避免把管理入口关掉。

部门负责人就是 `dept_leader` 在该部门上的未结束绑定。流程要找「发起人部门的负责人」时，用发起人的主部门 id 查询这个角色。主部门为空则没有负责人。这里不把下级部门的负责人算进上级部门。

## 3. 主体事实

权限模块在做访问判定前读取一名用户的事实。本接口不返回 SQL。

`GET /api/v1/org/actors/{id}`

用户不存在时 404。用户存在时始终返回 200。状态不是 `active` 时，部门数组和角色数组为空，`primaryDeptId` 为 `null`。这样停用用户不会因为旧任职而带上数据范围。

`active` 用户的计算方式：

1. `deptIds`：未结束任职上的部门 id。
2. `primaryDeptId`：其中 `is_primary = 1` 的部门；没有则为 `null`。
3. `deptIdsWithDescendants`：对 `deptIds` 里每个部门取闭包表中的下级（含自身），去重。停用的下级部门也包含在内，数据范围不随部门停用而漏掉历史单据；新建引用仍由部门模块拒绝停用部门。
4. `roles`：该用户未结束的绑定，且角色状态为 `active`。`dept_id = 0` 的项在 JSON 里写成 `deptId: null`。

```json
{
  "userId": "15",
  "status": "active",
  "primaryDeptId": "10",
  "deptIds": ["10", "12"],
  "deptIdsWithDescendants": ["10", "11", "12"],
  "roles": [
    { "code": "platform_admin", "deptId": null },
    { "code": "dept_leader", "deptId": "10" }
  ]
}
```

权限模块用这份结果决定能否调用数据 API，并把部门范围编译成谓词，交给数据读写模块挂到用户筛选条件的外面。主体事实在一次请求内读取一次，不放进业务事务里加锁。

## 4. 接口

| 方法与路径 | 作用 |
|---|---|
| `POST /api/v1/org/roles` | 创建自定义角色。请求给出 `code`、`title`、`scope` |
| `PATCH /api/v1/org/roles/{id}` | 修改显示名 |
| `POST /api/v1/org/roles:query` | 按编码、范围、状态查询 |
| `POST /api/v1/org/roles/{id}:disable` | 停用自定义角色 |
| `POST /api/v1/org/roles/{id}:enable` | 启用自定义角色 |
| `POST /api/v1/org/role-bindings` | 新建绑定 |
| `POST /api/v1/org/role-bindings/{id}:end` | 结束绑定 |
| `POST /api/v1/org/role-bindings:query` | 按角色、用户、部门、是否未结束查询 |
| `GET /api/v1/org/actors/{id}` | 读取主体事实 |

## 5. 错误

| HTTP | 何时 |
|---|---|
| 400 | 编码或 `scope` 不合法；组织范围角色带了部门；部门范围角色的 `deptId` 为 0 |
| 401 | 未登录 |
| 403 | 非 `platform_admin` 执行写操作；读取他人的主体事实 |
| 404 | 角色、用户、部门或绑定不存在 |
| 409 | 编码冲突；`rowVersion` 不匹配；重复的未结束绑定；停用或改状态作用在系统角色上；结束最后一名平台管理员的绑定；用户或角色不是 `active` |

权限模块调用 `GET /api/v1/org/actors/{id}` 时使用服务端身份，不受「只能读自己」这条限制。

## 6. 本模块完成标准

- 初始化后存在 `platform_admin` 和 `dept_leader`。第一名用户的主体事实含 `platform_admin`，且 `deptId` 为 `null`。
- 把一名用户绑成某部门的 `dept_leader` 后，事实中的对应项带有该部门 id。结束后该项消失，绑定行仍可按已结束查询到。
- 停用自定义角色后，未结束绑定还在，主体事实不再列出该角色。启用后重新出现。
- 停用用户的主体事实返回他的 `status`，部门数组和角色数组为空。
- 只剩一名有效平台管理员时，结束他的 `platform_admin` 绑定返回 409，绑定保持未结束。
