# 用户与组织

产品名称用「用户与组织」。一个部署是一个组织，下面有多个应用。本目录描述这个组织里的人、部门和授权分组。业务数据仍归 [数据模型](../数据模型/README.md)。

阅读顺序与落地顺序相同。

| 模块 | 文档 | 职责 |
|---|---|---|
| 1. 用户 | [01-用户](01-用户.md) | 登录名、姓名、状态、口令、外部身份 |
| 2. 部门与职位 | [02-部门与职位](02-部门与职位.md) | 部门树、闭包、职位名录、任职 |
| 3. 组织角色 | [03-组织角色](03-组织角色.md) | 角色、绑定、部门负责人，以及给权限模块的主体事实 |

## 要落地的能力

1. 管理员能创建用户、停用、办理离职，并用登录名与口令确认这个人可以进入系统。
2. 部门是一棵树。人通过任职进入部门，任职上可以带一个职位。每人最多一个主部门。
3. 组织角色把人分成稳定的组。`platform_admin` 管理本模块；`dept_leader` 按部门绑定。权限模块和流程只消费这些事实，不在这里配置策略或节点。

## 和其他模块的边界

本模块拥有平台表 `org_*`。用户 id 就是数据模型里的 `created_by`、`updated_by` 和变更历史里的 `actor_id`。没有登录主体的系统调用继续使用 `0`，`0` 不是 `org_user` 的合法 id。

业务单据要选人、选部门时，建成指向本模块的 `ref`，不在业务表里另放裸的成员 id 列。目录侧的接法：

- 平台初始化时登记保留应用，编码 `org`。该应用不通过结构 API 增删实体。
- 在这个应用下登记两条系统实体，编码 `user`、`department`。`dm_entity.table_name` 分别是 `org_user`、`org_department`。`title_field` 分别是 `display_name`、`title`。`soft_delete = 0`。物理表由本模块的初始化脚本创建，不走结构任务。
- 数据写入接口拒绝目标应用为 `org` 的创建、更新和删除。结构 API 拒绝修改应用 `org`。
- 引用校验和 `expand` 读这两张表：新建引用只接受 `active` 的用户和 `active` 的部门；已经写下的 id 在用户离职或部门停用后仍然能解析出标题。
- 沿 `user`、`department` 做列表筛选时，只允许目录里登记过的标量字段。部门的上下级不做成目录关联，筛选「某部门的下级」由权限模块用闭包表生成谓词。

职位、组织角色第一期不登记成实体。业务表需要时再增加对应的系统实体。

权限模块向本模块读取 [主体事实](03-组织角色.md)。它自己把事实编译成数据 API 的范围谓词。本模块不生成 SQL，也不保存数据范围。

流程要指定办理人时，引用用户 id、主部门或 `dept_leader` 绑定。办理人规则写在流程模块。

本模块的管理写接口只认系统角色 `platform_admin`，不回调权限模块，避免两边互相依赖。

## 共用约定

表使用 `InnoDB`、`utf8mb4`、`utf8mb4_0900_ai_ci`。时间列是 `DATETIME(3)`，存 UTC。写入路径不使用 `NOW()`、`CURRENT_TIMESTAMP` 和会话时区。

主键 `id` 是 `BIGINT UNSIGNED` 自增。JSON 里的 id、`rowVersion` 用十进制字符串，用 JSON 数字则返回 400。

部门、职位、角色的编码规则与数据模型相同：`^[a-z][a-z0-9_]{0,39}$`。创建后不改。显示名可以改。用户的登录名、工号不使用这套编码，规则见 [用户](01-用户.md)。

主对象带 `row_version`。更新请求带上读到的版本，不匹配则 409。同一次事务里无论改多少张组织表，涉及的行版本各加 1。

任职和角色绑定用 `open_token` 表示是否仍有效：未结束为 `0`，结束后写成该行自己的 `id`。需要「同一组合只有一条当前记录」的唯一索引把 `open_token` 放进键里。结束后的行保留，供查询曾经的任职和绑定。

状态取值：

| 对象 | 状态 |
|---|---|
| 用户 | `active`、`disabled`、`left` |
| 部门、职位、角色 | `active`、`disabled` |

`left` 只用于用户，第一期不能改回。`disabled` 可以再启用。

## 初始化

空库启动时在一个事务里写入：

1. 保留应用 `org`，以及实体 `user`、`department` 的目录行。
2. 根部门，编码 `root`，名称由部署参数给出，`parent_id` 为空。闭包表写入自身，深度 `0`。
3. 系统角色 `platform_admin`（组织范围）和 `dept_leader`（部门范围）。
4. 第一名用户、他的口令，以及一条 `platform_admin` 绑定。部署参数没有提供第一名用户时，拒绝启动业务端口。

根部门不能移动、不能停用、不能删除。两个系统角色不能停用、不能删除，编码不能改，显示名可以改。

## 第一期做完的标准

- 能创建用户并凭登录名完成校验；停用后校验失败；离职后 `created_by` 仍能解析出姓名。
- 能把部门移到另一个父部门下，闭包与父子关系一致；移到自己的下级时整次请求失败。
- 一个人可以有多条未结束任职，其中最多一条主部门。
- `platform_admin` 能管理用户、部门和角色。`dept_leader` 按部门绑定后，主体事实里能看到对应的部门 id。
- 业务实体可以 `ref` 到 `user` 和 `department`。数据写入接口不能改这两张表。
