# 登录方式

职责：把一种凭据解析成唯一的 `org_user`，确认状态为 `active`，再交给 [会话](04-会话.md) 签发。管理端和各应用 client 走同一条管道，不按应用分登录方式。

不负责：会话如何保存和携带；从身份源拉取部门或人员；权限和菜单。应用代码不实现登录，解释器里没有这组接口。

依赖：[用户](01-用户.md) 的口令、状态和 `org_external_identity`。[会话](04-会话.md) 负责签发。

一个部署一种配置。身份源不是应用级对象。

## 1. 管道

1. 按登录方式验证凭据。
2. 得到至多一名用户。找不到、找到多名、或凭据无效，都返回同一个 401，正文不说明原因。
3. 用户状态不是 `active` 时返回同一个 401。
4. 交给会话签发。

`auth:verify` 仍只校验登录名和口令，不写 cookie。`auth:login` 是进入系统的入口。

## 2. 方式

| 方式 | 何时 | 解析结果 |
|---|---|---|
| 登录名 + 口令 | 第一期 | `org_credential` 匹配，且用户为 `active` |
| OIDC 授权码 | 企业接入时 | 回调中的主体 id 对应 `org_external_identity` 的一行，`provider` 为该身份源编码 |
| 企业微信、钉钉 | 企业接入时 | 同上，`provider` 分别为 `wecom`、`dingtalk` |
| LDAP 或 AD 绑定 | 再往后 | 只校验口令并找到已有用户。不从目录写入部门和任职 |
| TOTP | 再往后 | 第二因素，加在口令或 OIDC 之后。先用于 `platform_admin`，不单独作为登录入口 |

个人微信、短信验证码、邮件链接不进入内核。

第一期的 `org_external_identity` 只做手工绑定。未开通的方式即使已经绑了外部 id，也不能用来登录。未绑定的外部主体返回 401，不自动创建用户。

OIDC、企业微信、钉钉落地时再写各自的跳转和回调字段。回调成功后的唯一下落是上面这条管道。

## 3. 第一期接口

`POST /api/v1/org/auth:login`

请求体是登录名和口令。校验规则与 `auth:verify` 相同：登录名不存在、口令不匹配、状态不是 `active`，都返回 401。成功则按 [会话](04-会话.md) 写 cookie，正文为用户 id、登录名和姓名。

## 4. 本模块完成标准

- 正确的登录名和口令完成本管道，并出现会话 cookie。
- 错误口令、停用、离职都不签发会话。
- 已经手工绑定的 `wecom` 或 `dingtalk` 外部 id，第一期不能用来登录。
