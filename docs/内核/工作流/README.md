# 工作流

产品名称用「工作流」。它保存流程定义、实例和待办，并按办理人规则把待办交给人。审批流是其中以人工节点为主的定义：同意和退回是人工节点的两种结果，不是另一套引擎。

业务数据仍归 [数据模型](../数据模型/README.md)。人、部门和 `dept_leader` 来自 [用户与组织](../用户与组织/README.md)。本目录不生成权限谓词，也不改 `org_*`。

阅读顺序与落地顺序相同。

| 模块 | 文档 | 职责 |
|---|---|---|
| 1. 流程定义 | [01-流程定义](01-流程定义.md) | 定义、版本、节点、边、发布 |
| 2. 办理人 | [02-办理人](02-办理人.md) | 人工节点解析成具体用户 |
| 3. 实例与待办 | [03-实例与待办](03-实例与待办.md) | 发起、同意、退回、待办查询 |
| 4. 推进 | [04-推进](04-推进.md) | 人工办理、变更消费、超时、领域函数与回写 |

## 要落地的能力

1. 管理员能为一张业务实体发布一张流程。发布后的版本不再修改。正在运行的实例停在它启动时的版本上。
2. 已登录用户能对一条业务记录发起流程，并在自己的待办上同意或退回。多名办理人时，第一人作出结果，其余待办取消。
3. 同意、退回和超时都沿定义好的边往下走。边上的 `write` 节点通过数据读写管线改业务行。`call` 节点调用已发布的领域函数。
4. 人工办理在 `api` 进程完成。变更触发的发起和超时在 `worker` 进程完成。两条路使用同一个调用入口。

## 和其他模块的边界

本模块拥有平台表 `wf_*`。流程定义归属应用，实体编码引用该应用里已经 `active` 的实体。目录不保存节点、边和办理人。

写业务表只走数据读写管线。执行业务动作只调用已发布领域函数，宿主按模块编码和函数名进入该模块的解释器池。不把 `/api/v1/domain/{appCode}/{funcName}` 挂到公网，也不为流程再开一种脚本或第二个解释器。

办理人只使用用户 id、发起人、发起人的主部门、发起人主部门上的 `dept_leader`。本模块不保存另一套组织树。

变更消费者的名字是 `wf`。进度和租约沿用 [变更历史](../数据模型/05-变更历史.md) 与 [多实例归属](../数据模型/08-多实例归属.md)。`worker` 调用领域函数时已经按总图为已发布模块建有解释器池。

管理写接口只认 `platform_admin`。待办的同意和退回只认该待办上的办理人，不回调权限模块做第二套动作许可。发起前对业务行做一次读，读挂点拒绝则不发起。

## 第一期不做

会签、加签、转办、办理中撤回、办理人临时指定退回节点、代理人。退回只沿定义里的 `reject` 边走。

## 第一期做完的标准

- 能发布一张含人工节点的请假流程。同意边上的 `write` 把业务行的状态字段写成通过，退回边写成驳回。规则失败时待办仍是待办，业务行不变。
- 同一条记录上，同一流程只有一个运行中实例。重复发起返回 409。
- 两名部门负责人同时同意，只有一个成功，另一人的待办变为已取消。
- 人工办理中领域函数失败则整单回滚，待办仍为 `open`。变更消费中领域函数返回业务错误时，回滚这次推进的业务写入，实例标为 `error`，游标前进。
- `worker` 因处理某条变更而写入的业务行带有 `cause_visible_seq`。这条新变更不会再次调用刚执行过的那个领域函数。
- 人工节点超时后，`worker` 以主体 `0` 沿 `timeout` 边推进。没有该边则待办继续开着。
