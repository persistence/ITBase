# 推进

职责：从当前节点沿一条边走到下一个需要等待的地方。人工点击在 `api` 进程执行。变更触发的发起和超时在 `worker` 进程执行。写业务行和调用领域函数都从这里进入。

不负责：节点和边的合法性（见 [流程定义](01-流程定义.md)）；待办表的字段（见 [实例与待办](03-实例与待办.md)）。

依赖：数据读写管线、已发布模块的解释器池、变更消费者 `wf`。`worker` 按总图为每个已发布模块持有解释器池，否则 `call` 无法在消费端执行。

## 1. 一次推进

从当前节点取出与本次结果对应的边，读终点，然后：

| 终点 | 动作 |
|---|---|
| `human` | 解析办理人并插入 `open` 待办。实例 `node_code` 改为该节点，状态保持 `running` |
| `write` | 经数据读写管线更新该实例的业务行。`source` 为 `system`。成功后继续沿它的 `ok` 边推进 |
| `call` | 在本进程借该模块的解释器，调用领域函数。成功后继续沿 `ok` 边推进 |
| `end` | 实例状态改为节点的 `end_status`，`node_code` 清空，`open_token` 写成实例 id |

连续的 `write` 和 `call` 在同一次推进里做完，直到进入人工节点或结束。不在 `call` 之后另起事务再标待办。

人工办理把上述步骤放进办理请求已经打开的事务。任一步失败则回滚，待办保持 `open`。

`write` 先按数据 API 的规则读出当前 `rowVersion`，再提交 `write_json` 里的字段。不写 JSON 里没有的字段。CEL、权限挂点和乐观锁与直接调用数据 API 相同。权限挂点的主体是下面第 3 节的主体。

`call` 的 `itb.Input.Body` 固定为：

| 键 | 值 |
|---|---|
| `instanceId` | 十进制字符串 |
| `recordId` | 十进制字符串 |
| `entityCode` | 流程绑定的实体编码 |
| `nodeCode` | 该 `call` 节点编码 |
| `outcome` | 进入这次推进的 `approve`、`reject`、`timeout` 或 `ok` |

领域函数里的 `Create`、`Update`、`Delete` 仍走数据读写管线。函数返回 `itb.Fail` 或任一写入失败，视为这次推进失败。

## 2. 变更触发

```sql
CREATE TABLE wf_trigger (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '触发主键',
  ver_id      BIGINT UNSIGNED NOT NULL COMMENT 'wf_ver.id',
  op          VARCHAR(16)     NOT NULL COMMENT 'create 或 update',
  field_code  VARCHAR(40)     NULL COMMENT 'update 时比较的字段。空表示任意更新',
  field_value VARCHAR(255)    NULL COMMENT 'after 快照中的值。decimal 与 bigint 用十进制字符串',
  PRIMARY KEY (id),
  UNIQUE KEY uk_wf_trigger (ver_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '已发布版本的启动触发。第一期至多一条';

CREATE TABLE wf_receipt (
  app_id      BIGINT UNSIGNED NOT NULL COMMENT '应用',
  visible_seq BIGINT UNSIGNED NOT NULL COMMENT '已处理的 dm_record_change.visible_seq',
  PRIMARY KEY (app_id, visible_seq)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '消费者 wf 的幂等回执';

CREATE TABLE wf_effect (
  app_id      BIGINT UNSIGNED NOT NULL COMMENT '应用',
  visible_seq BIGINT UNSIGNED NOT NULL COMMENT '正在处理的变更序号',
  proc_id     BIGINT UNSIGNED NOT NULL COMMENT '这次推进碰到的流程',
  module_code VARCHAR(40)     NOT NULL DEFAULT '' COMMENT 'call 节点的模块。只有 write 时为空字符串',
  func_name   VARCHAR(80)     NOT NULL DEFAULT '' COMMENT 'call 节点的函数。只有 write 时为空字符串',
  PRIMARY KEY (app_id, visible_seq, proc_id, func_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '一次消费推进了哪张流程的哪个函数。用于拦住重入';
```

草稿的 `PUT` 可以带这一条触发，随版本发布。没有触发的流程只能由 `:start` 发起。

消费者名字是 `wf`。只有持有该租约的 `worker` 读取 `dm_record_change`。对每条 `visible_seq` 大于游标的变更：

1. 回执已存在则跳过。
2. 若该变更的 `cause_visible_seq` 非空，读出对应的 `wf_effect`。这些 `proc_id` 不再用本条变更去启动，这些 `func_name` 不再被本条变更调用。其他流程的启动触发仍可匹配。
3. 流程为 `active`，变更的实体等于流程的 `entity_code`，`op` 与触发一致。`update` 还要求 `after_json.values` 里该字段等于 `field_value`。
4. 该记录没有 `running` 实例时，按发起规则创建实例。`started_by` 使用变更上的 `actor_id`。`actor_id` 为 `0` 或用户已不是 `active` 时，不发起，回执照写。
5. 成功时，回执、`wf_effect`、实例和业务写入在同一事务提交，然后按 [变更历史](../数据模型/05-变更历史.md) 的 CAS 推进 `last_seq`。

同一 `visible_seq` 至少会投递一次。回执使第二次投递不再发起。

由这次消费写入的每一条 `dm_record_change` 把 `cause_visible_seq` 设为正在处理的序号。人工 `:start` 和人工办理产生的写入把该列留空。

领域函数返回业务错误，或办理人解析为空时：回滚这次推进里的业务写入。另开一个短事务，把已经需要留下的实例标为 `error`，写入回执。游标随后前进，避免一条配置错误堵住该应用后面的变更。解释器池不可用、进程 panic、数据库错误：不写回执，不前进游标，按变更历史的退避重试。

## 3. 主体

| 来源 | 主体 |
|---|---|
| 人工发起、同意、退回 | 当前登录用户 |
| 变更触发的发起和随后的 `write`、`call` | 该变更的 `actor_id` |
| 超时 | `0` |

权限挂点把 `0` 识别为工作流的系统调用，只放行本模块在超时推进里发起的写入。`0` 不能用来调用对外的数据 API。

## 4. 超时

`worker` 每秒读取 `status = open` 且 `due_at` 不为空、并且 `due_at` 早于当前 UTC 时间的待办。当前时间由应用时钟给出，不在 SQL 里使用 `NOW()`。

处理一条超时待办时锁住实例。待办已不是 `open` 则跳过。有 `timeout` 边时，以主体 `0` 沿该边推进，并把其余同节点待办标为 `cancelled`。没有 `timeout` 边时不修改待办。

超时推进与人工办理使用同一套节点动作。两人刚提交同意、超时也读到这条待办时，后拿到锁的一方看到待办已结束并停止。

## 5. 本模块完成标准

- 人工同意后，`write` 节点把业务字段写成定义中的字面值。CEL 失败时待办仍为 `open`，业务行的 `rowVersion` 不变。
- `call` 节点收到的 `Body` 含 `instanceId`、`recordId`、`entityCode`、`nodeCode`、`outcome`。函数内的 `Update` 与直接调用数据 API 一样触发 CEL。
- 函数在人工请求里返回 `itb.Fail` 时，待办仍为 `open`。同一函数在变更消费里返回 `itb.Fail` 时，实例为 `error`，游标越过这条 `visible_seq`。
- 消费写入的变更带有 `cause_visible_seq`。下一次消费不再次调用同一个 `func_name`。另一张流程若触发条件匹配，仍可以发起。
- 人工节点设置 1 分钟超时时，到期后 `worker` 沿 `timeout` 边进入结束节点，实例状态与该结束节点的 `end_status` 一致。
