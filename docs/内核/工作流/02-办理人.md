# 办理人

职责：把人工节点上的一条规则，在实例走到该节点时解析成若干 `active` 用户，并为每人生成一条待办。

不负责：流程画布（见 [流程定义](01-流程定义.md)）；待办的同意和退回（见 [实例与待办](03-实例与待办.md)）。本模块不读取权限策略。

依赖：[组织角色](../用户与组织/03-组织角色.md) 的主体事实，以及 [部门与职位](../用户与组织/02-部门与职位.md) 的未结束任职。只用发起人的主部门，不把下级部门的负责人算进上级部门。

## 1. 规则

```sql
CREATE TABLE wf_assign (
  id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '规则主键',
  ver_id    BIGINT UNSIGNED NOT NULL COMMENT 'wf_ver.id',
  node_code VARCHAR(40)     NOT NULL COMMENT 'human 节点编码',
  kind      VARCHAR(16)     NOT NULL COMMENT 'user、initiator、primary_dept、dept_leader',
  user_id   BIGINT UNSIGNED NULL COMMENT 'kind 为 user 时必填，且发布时该用户为 active',
  PRIMARY KEY (id),
  UNIQUE KEY uk_wf_assign (ver_id, node_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '人工节点的办理人规则。第一期每节点一条';
```

| kind | 运行时解析 |
|---|---|
| `user` | 这一名用户。当时状态不是 `active` 则解析为空 |
| `initiator` | 实例的 `started_by`。状态不是 `active` 则解析为空 |
| `primary_dept` | 发起人主部门上全部未结束任职的用户，且用户为 `active`。没有主部门则解析为空 |
| `dept_leader` | 发起人主部门上 `dept_leader` 的未结束绑定，且用户和角色都有效。没有主部门则解析为空 |

第一期一个人工节点只有一条规则。解析出多名用户时是或签：每人一条待办，任何一人提交结果后，其余待办取消。会签不在第一期。

解析结果按用户 id 去重。空结果视为配置或组织事实不满足，不创建零办理人的待办。由人工请求走到该节点时，整个办理或发起回滚并返回 422。由 `worker` 走到该节点时，实例变为 `error`，规则见 [推进](04-推进.md)。

固定用户在发布时就要是 `active`。发起人、主部门和负责人留到实例走到该节点时再算，因为任职和绑定会变。

## 2. 和定义接口的关系

[流程定义](01-流程定义.md) 的草稿 `PUT` 一并提交办理人。人工节点缺少规则，或 `user` 没有 `userId`，发布返回 422。非人工节点不能带规则。

JSON 里的 `userId` 是十进制字符串。用 JSON 数字则返回 400。

## 3. 本模块完成标准

- `dept_leader` 规则在发起人主部门有两名负责人时，产生两条待办。一人同意后另一条为 `cancelled`。
- 发起人没有主部门时，`dept_leader` 与 `primary_dept` 都不产生待办。人工发起因此 422，不留下 `running` 实例。
- 规则写成固定用户后该用户离职，新走到该节点时解析为空。已经生成的待办不自动转给别人。
