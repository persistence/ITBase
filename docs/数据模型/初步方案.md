# 数据模型初步方案

结构变更、CEL 校验、主表连带关联表写入，收在同一套数据模型里。结构 API 改的是模型并同步物理表；写入 API 只认已经生效的模型。校验规则用 CEL 文本保存，服务端用 cel-go 编译执行，浏览器执行同一段 CEL。

产品名称用「数据模型」。代码里实体为 `entity`，字段为 `field`。文档需要强调「描述结构的数据」时，再用「元数据」。

## 1. 能力划分

| 能力 | 接口 | 作用对象 |
|---|---|---|
| 结构增删改 | `/api/models/...` | 实体、字段、关联、索引、校验规则 |
| 运行时描述 | `GET /api/models/entities/{code}/runtime` | 给前端表单和 CEL 用 |
| 数据读写 | `/api/data/{entityCode}` | 当前表和关联表 |
| 规则试算 | `POST /api/models/entities/{code}/rules:test` | 不落库，只返回校验结果 |

物理库使用 PostgreSQL。一个实体一张 `biz_{code}` 表。

三块数据分开存放：

| 块 | 存什么 | 何时写入 |
|---|---|---|
| 模型 | 实体、字段、关联、索引、校验规则 | 结构 API |
| 已生效版本 | 实体清单快照、DDL、JSON Schema | 结构变更成功时 |
| 业务表 | 用户记录 | 数据写入 API |

页面、流程、权限只引用已生效的 `entityCode` 和 `fieldCode`。显示名可以改，编码生效后不可改。

## 2. 名词

| 概念 | 界面 | 代码 |
|---|---|---|
| 整块能力 | 数据模型 | `model` |
| 一类业务数据 | 实体 | `entity` |
| 实体上的一项属性 | 字段 | `field` |
| 一条业务数据 | 记录 | `record` |
| 实体之间的连接 | 关联 | `relation` |
| 某次冻结下来的结构 | 版本 | `revision` |
| 校验表达式 | 校验规则 | `rule` |

物理表只在迁移和库设计里叫表，不进产品菜单。

## 3. 模型表

### 3.1 dm_entity

| 列 | 说明 |
|---|---|
| id | 主键 |
| code | 实体编码，创建后不可改，如 `customer` |
| title | 显示名，可改 |
| table_name | 物理表名，创建时定为 `biz_{code}`，之后不可改 |
| title_field | 标题字段编码，用于关联选择器的默认展示 |
| published_revision | 当前已生效版本 |
| deleted_at | 停用时间；停用后不再接受写入 |

### 3.2 dm_field

| 列 | 说明 |
|---|---|
| entity_id | 所属实体 |
| code | 字段编码，生效后不可改 |
| title | 显示名 |
| type | 见第 4 节 |
| required / unique | 约束 |
| default_value | JSON 存默认值 |
| length | 文本长度 |
| precision / scale | 小数精度 |
| option_set_code | 选项字段引用的选项集 |
| target_entity | 关联的目标实体 |
| relation | `many_to_one` 或 `many_to_many` |
| on_delete | `restrict`、`set_null`、`cascade` |
| column_name | 物理列名，生效后不可改 |
| system | 系统字段，不可删 |
| deprecated | 废弃后接口不再读写，列先保留 |
| sort | 设计器排序 |

### 3.3 dm_option_set / dm_option_item

选项集编码、显示名。选项的 `value` 生效后不可改，`label` 可改。选项字段的物理列存 `value`，类型为 `varchar(64)`。

### 3.4 dm_index

索引编码、是否唯一、字段编码列表。

### 3.5 dm_rule

| 列 | 说明 |
|---|---|
| entity_id | 所属实体 |
| code | 规则编码 |
| title | 显示名 |
| trigger | `create`、`update`、`write` |
| expression | CEL 源文本 |
| message | 校验失败时返回的文案 |
| enabled | 是否启用 |
| sort | 执行顺序 |

### 3.6 dm_revision

`entity_id`、`revision`、实体清单快照、本次 DDL、创建用 JSON Schema、更新用 JSON Schema、生效时间。

创建实体时自动写入系统字段，且 `system = true`：

| 字段 | 物理列 | 类型 |
|---|---|---|
| id | id | `bigint generated always as identity` |
| created_at | created_at | `timestamptz` |
| created_by | created_by | `bigint` |
| updated_at | updated_at | `timestamptz` |
| updated_by | updated_by | `bigint` |
| deleted_at | deleted_at | `timestamptz` |

## 4. 字段类型与落列

| type | 物理列 | 第一期约束 |
|---|---|---|
| string | `varchar(length)`，默认 255 | 必填、唯一、最大长度 |
| text | `text` | 必填 |
| integer | `bigint` | 必填、唯一 |
| decimal | `numeric(precision, scale)` | 必填 |
| boolean | `boolean` | 必填时默认 `false` |
| date | `date` | 必填 |
| datetime | `timestamptz` | 必填 |
| option | `varchar(64)`，存选项 value | 值必须属于选项集 |
| relation | 见下 | 目标实体必须已存在 |

关联只让调用方建两种：

- **多对一**：在当前表加列 `{code}_id`，外键指向目标表 `id`。一对一是这种字段再加唯一索引。
- **多对多**：建中间表 `biz_{实体}_{字段编码}`，两列外键组成主键。
- **一对多**：不单独建字段。目标实体上有指向本实体的多对一字段时，读取侧自动带出。

附件做成指向系统实体 `file` 的多对一。上传本身不属于数据模型。

## 5. 实体清单

导入、导出和版本快照使用这份 JSON。它是源文件。JSON Schema 由它编译生成，不手写，也不回写。

```json
{
  "code": "customer",
  "title": "客户",
  "table": "biz_customer",
  "titleField": "name",
  "fields": [
    {
      "code": "name",
      "title": "客户名称",
      "type": "string",
      "required": true,
      "unique": true,
      "length": 100,
      "column": "name"
    },
    {
      "code": "level",
      "title": "客户等级",
      "type": "option",
      "optionSet": "customer_level",
      "column": "level"
    },
    {
      "code": "owner",
      "title": "负责人",
      "type": "relation",
      "relation": "many_to_one",
      "target": "employee",
      "onDelete": "set_null",
      "column": "owner_id"
    }
  ],
  "indexes": [
    { "code": "uk_name", "unique": true, "fields": ["name"] }
  ],
  "rules": [
    {
      "code": "name_present",
      "trigger": "write",
      "expression": "name.size() > 0",
      "message": "客户名称不能为空"
    }
  ]
}
```

系统字段不进这份清单，创建和结构变更时由平台补上。

## 6. 表结构 API

每个结构变更接口都做三件事：更新模型、生成 DDL、在同一个事务里执行。失败时模型和物理表一起回到调用前。

```
POST   /api/models/entities
PATCH  /api/models/entities/{code}
DELETE /api/models/entities/{code}

POST   /api/models/entities/{code}/fields
PATCH  /api/models/entities/{code}/fields/{fieldCode}
DELETE /api/models/entities/{code}/fields/{fieldCode}

POST   /api/models/entities/{code}/indexes
DELETE /api/models/entities/{code}/indexes/{indexCode}

PUT    /api/models/entities/{code}/relations/{fieldCode}

POST   /api/models/entities/{code}/rules
PATCH  /api/models/entities/{code}/rules/{ruleCode}
DELETE /api/models/entities/{code}/rules/{ruleCode}
```

创建实体：

```json
{
  "code": "order",
  "title": "订单",
  "titleField": "order_no",
  "fields": [
    { "code": "order_no", "title": "订单号", "type": "string", "required": true, "unique": true, "length": 32 },
    { "code": "amount", "title": "金额", "type": "decimal", "precision": 18, "scale": 2, "required": true },
    {
      "code": "customer",
      "title": "客户",
      "type": "relation",
      "relation": "many_to_one",
      "target": "customer",
      "required": true,
      "onDelete": "restrict"
    }
  ]
}
```

一次要改多项时走变更集，避免接口调用到一半库已经变了：

```
POST /api/models/changesets
POST /api/models/changesets/{id}:apply
```

`code`、物理表名、物理列名生效后固定。显示名可以随时改。

| 操作 | 第一期行为 |
|---|---|
| 新建实体 | 建 `biz_{code}`，带系统字段 |
| 加可空字段 | 直接 `ADD COLUMN` |
| 加必填字段 | 必须带默认值 |
| 加长字符串 | 允许 |
| 加索引、改默认值、改删除策略 | 允许 |
| 改字段类型、改 code、缩短字符串 | 接口直接拒绝 |
| 删除字段 | 默认只废弃：接口不再读写，列保留 |
| 物理删字段 / 删表 | 查询参数 `physical=true`，并要求调用方显式确认 |

成功后写入一条 `dm_revision`，并更新 `published_revision`。

## 7. 校验规则

规则是实体上的 CEL 表达式，随模型一起保存、一起生效。保存时用 cel-go 按该实体的字段类型编译，输出类型必须是布尔；编译失败则规则不入库。

cel-go 跑在服务端。浏览器执行的是同一段 CEL 文本。两侧只开放同一子集：比较、算术、逻辑运算、三元表达式、`size`、`startsWith`、`contains`、`has`。第一期不开放自定义函数、聚合和查库。

```
POST /api/models/entities/order/rules
```

```json
{
  "code": "amount_positive",
  "title": "金额必须大于 0",
  "trigger": "write",
  "expression": "amount > 0.0",
  "message": "金额必须大于 0"
}
```

触发时机：

| trigger | 何时执行 |
|---|---|
| create | 仅创建 |
| update | 仅更新 |
| write | 创建和更新 |

更新表达式可以读 `old`，例如 `old.amount <= amount`。

变量就是字段编码，类型按字段映射：

| 字段类型 | CEL 类型 |
|---|---|
| string、text、option | string |
| integer、关联外键 | int |
| decimal | double |
| boolean | bool |
| date、datetime | string，格式 `YYYY-MM-DD`、RFC3339 |

关联字段在表达式里先只出现外键，如 `customer_id`。子表记录用子表自己的规则校验。表达式不能访问数据库。

服务端把编译结果按「实体 + 模型版本」缓存。字段类型再变更时，先用 cel-go 重编译全部规则，有一条失败就拒绝这次结构变更。

前端从 runtime 接口拿规则，在失焦和提交时求值，错误文案用规则上的 `message`。提交后服务端再执行一次。

一致性用同一份用例保证：`{ expression, input, expected }`，Go 和前端 CEL 都要跑过。

试算：

```json
POST /api/models/entities/order/rules:test
{ "values": { "amount": 0 }, "trigger": "create" }
```

## 8. 写入当前表和关联表

一次请求、一个数据库事务。任意一行校验失败或写库失败，整次请求回滚。

```
GET    /api/data/{entityCode}
POST   /api/data/{entityCode}
GET    /api/data/{entityCode}/{id}
PATCH  /api/data/{entityCode}/{id}
DELETE /api/data/{entityCode}/{id}
```

写入示例：

```json
POST /api/data/order
{
  "order_no": "SO001",
  "amount": 30,
  "customer": { "id": 12 },
  "lines": [
    { "sku": "A", "qty": 2, "price": 10 },
    { "sku": "B", "qty": 1, "price": 10 }
  ]
}
```

关联字段用字段编码 `customer`、`lines`，由服务端映射到外键或中间表。

| 节点 | 行为 |
|---|---|
| 标量字段 | 写入当前表 |
| 关联对象只有 `id` | 只建立关联 |
| 关联对象没有 `id` | 先插入关联表，再回填当前表 |
| 数组元素有 `id` | 更新该行 |
| 数组元素没有 `id` | 插入子表，外键指向当前记录 |
| `_op: "delete"` | 软删除该行 |
| 多对多 `_op: "link"` / `"unlink"` | 只改中间表 |

未出现在数组里的旧子记录保持不动。深度最多 3 层，单次最多 200 个节点。

列表查询使用白名单，不接收 SQL：

```json
{
  "filter": { "order_no": { "$contains": "SO" }, "amount": { "$gt": 0 } },
  "sort": ["-created_at"],
  "page": 1,
  "pageSize": 20
}
```

`$eq`、`$contains`、`$gt`、`$in` 按字段类型开放。列名只从已生效字段的 `column_name` 里取。删除写 `deleted_at`，列表默认不返回已删除记录。

读取关联：`GET /api/data/order/1?include=customer,lines`。返回字段和写入字段对齐。

### 8.1 写入顺序

1. 按已生效模型解析请求树，拒绝未知字段和超限深度。
2. 多对一的新建对象先插入，保证当前表外键有值。
3. 插入或更新当前表。
4. 处理一对多子表和多对多中间表。
5. 对每个碰到的实体跑对应 CEL。
6. 提交。

### 8.2 JSON Schema

发布结构变更时由字段编译两份，存进 `dm_revision`：

- 创建：不含 `id` 和系统时间字段，`required` 来自字段定义，`additionalProperties` 为 `false`。
- 更新：全部业务字段可选，同样拒绝未定义字段。

`customer.name` 编译为 `{ "type": "string", "maxLength": 100 }`。`owner` 编译为 `owner_id`，类型为整数。多对多不放进这条记录的 Schema，用关联节点读写。

JSON Schema 负责类型、必填、长度。跨字段条件放在 CEL 里。

### 8.3 错误

```json
{
  "code": "validation_failed",
  "errors": [
    { "path": "amount", "rule": "amount_positive", "message": "金额必须大于 0" },
    { "path": "lines[0].qty", "rule": "qty_positive", "message": "数量必须大于 0" }
  ]
}
```

## 9. 前端使用的 runtime

```
GET /api/models/entities/order/runtime
```

返回已生效的字段、关联、CEL 规则、创建和更新用的 JSON Schema、模型版本号。前端用它渲染表单，并在浏览器里执行同一套 CEL。

## 10. 第一期范围

第一期做到：

1. 实体、字段、多对一、多对多的新增、修改、废弃和受控物理删除。
2. CEL 规则随结构 API 保存，cel-go 编译不过不能生效；前端用同一表达式做录入校验。
3. 单请求事务写入当前表和关联表，主表与子表规则都执行。
4. runtime 接口能驱动表单渲染和浏览器侧 CEL。
5. 通用接口能完成增删改查；非法类型、未知字段、不存在的关联被拒绝。

第一期不包含：

- 表达式里查库或汇总子表
- 字段类型互转
- 从已有库反向导入
- 字段级权限
- 公式字段、ER 图

子表汇总类规则等两侧 CEL 子集稳定后再加 `all` / `exists`。
