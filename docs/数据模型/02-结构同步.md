# 结构同步

职责：把目录里的目标结构落到 MySQL 物理表。管理结构任务、在事务外执行 DDL、失败重试，以及目录与 `information_schema` 的核对。

不负责：目录对象的业务含义与允许改哪些结构（见 [元数据目录](01-元数据目录.md)）；业务行 DML（见 [数据读写](04-数据读写.md)）。

依赖：元数据目录。收紧列之前还要读 [多实例归属](09-多实例归属.md) 的实例心跳。数据读写只消费本模块已经标成 `active` 的列和索引。

## 1. dm_schema_task

```sql
CREATE TABLE dm_schema_task (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '任务主键',
  entity_id    BIGINT UNSIGNED NOT NULL COMMENT '目标实体，dm_entity.id。同一实体的任务按它串行',
  depends_on   BIGINT UNSIGNED NULL COMMENT '前置任务 id。前置 applied 之前本行为 blocked',
  action       VARCHAR(32)     NOT NULL COMMENT 'create_table、add_column、modify_column、drop_column、add_index、drop_index、create_junction、drop_junction',
  target_kind  VARCHAR(16)     NOT NULL COMMENT '目录对象种类：entity、field、link、index',
  target_id    BIGINT UNSIGNED NOT NULL COMMENT '目录对象 id，与 target_kind 一起指向被变更的行',
  forward_ddl  TEXT            NOT NULL COMMENT '正向 DDL。重试时先对照 information_schema，定义已到位则不再执行',
  reverse_ddl  TEXT            NULL COMMENT '逆向 DDL。purge 为空，数据不能自动找回',
  status       VARCHAR(16)     NOT NULL COMMENT 'blocked、pending、running、applied、failed',
  error_text   TEXT            NULL COMMENT 'DDL 或核对失败时的 MySQL 错误',
  created_at   DATETIME(3)     NOT NULL COMMENT '插入时间，UTC',
  started_at   DATETIME(3)     NULL COMMENT '改为 running 的时间，UTC',
  applied_at   DATETIME(3)     NULL COMMENT '改为 applied 的时间，UTC',
  PRIMARY KEY (id),
  KEY idx_dm_schema_task_entity (entity_id, status),
  KEY idx_dm_schema_task_depends (depends_on)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '结构任务。目录事务插入，DDL 在事务外执行';
```

`action`：`create_table`、`add_column`、`modify_column`、`drop_column`、`add_index`、`drop_index`、`create_junction`、`drop_junction`。

`status`：`blocked`、`pending`、`running`、`applied`、`failed`。

`blocked` 表示目录已经记下后续步骤，但前置任务还没 `applied`。同一实体可以同时有一条 `pending` 或 `running`，以及若干条 `blocked`。`blocked` 不参与执行。前置任务 `applied` 后，执行器把直接依赖它的 `blocked` 任务改成 `pending` 再执行。

同一实体只要还有 `pending`、`running`、`blocked` 或未放弃的 `failed`，结构 API 就拒绝新的结构变更。保证方式是锁住 `dm_entity` 行。关联同时锁两侧，顺序为实体 id 升序。

管理接口：

```text
GET    /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}
POST   /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}:retry
POST   /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}:abandon
```

GoFrame 侧，目录与业务 DML 走 `gdb` 事务；DDL 用单独的连接，不包在 `Transaction` 回调里。

## 2. 一次结构变更的顺序

以新增字段为例：

1. 校验编码、类型、长度、选项集是否属于同一应用，并写入 `dm_name`。
2. 开启短事务，锁 `dm_entity`。若该实体已有未完成任务，返回 409。
3. 插入 `dm_field`，`status = pending`。插入 `dm_schema_task`，写好 `forward_ddl` 与 `reverse_ddl`。有后续步骤时，后续任务在这次事务里插入，`status = blocked`，`depends_on` 指向第一步。提交。
4. 事务提交后，本进程执行器申请执行。请求是否一直等到 DDL 结束，见第 5 节。
5. 执行器从连接池拿出**一条**连接，并在这条连接上完成 `GET_LOCK('dm_schema_{entityId}')`、DDL、`RELEASE_LOCK`。锁和 DDL 不能拆到池里的两条连接上，否则锁会提前释放。
6. 拿到锁后，把任务从 `pending` 条件更新为 `running`（`WHERE status = 'pending'`）。影响行数为 0 则退出：别的副本已经在跑或已经跑完。
7. 按第 3 节对照 `information_schema`。已经是目标定义则跳过 DDL，直接进入成功收尾。仍是旧定义则执行 `forward_ddl`。两边都不是则把任务标成 `failed`，不执行 DDL。
8. DDL 成功：任务改为 `applied`，字段改为 `active`，`dm_entity.revision` 加 1。若有 `blocked` 后续任务，放行下一条并继续在同一把命名锁里执行。
9. DDL 失败：任务改为 `failed`，字段改为 `failed`，`error_text` 记下 MySQL 错误。

状态更新使用 `WHERE status = 'running'`，避免两台进程同时把同一任务收成 `applied`。

`retry` 只接受 `failed` 任务。它把任务改回 `pending` 后走同一步骤 5。判据仍是第 3 节，不是「列在不在」。

`:abandon` 的目录删除见 [元数据目录 6.3](01-元数据目录.md)。放弃前必须用第 3 节确认目标定义尚未出现。

创建实体时，系统字段行与 `create_table` 任务在同一次目录事务里插入，状态为 `pending`。任务 `applied` 后，实体和系统字段一起改为 `active`。不要等 DDL 成功后再补插系统字段，那一步崩溃会留下没有目录行的物理表。

## 3. 怎样判断 DDL 已经生效

对照使用目录里记下的物理名和目标定义。只报告或确认，不在核对接口里自动删列。

| action | 视为已生效 | 视为仍可执行 forward_ddl |
|---|---|---|
| `create_table` | `information_schema.TABLES` 有该表，且系统列的类型与可空与第 1 模块的建表语句一致 | 表不存在 |
| `add_column` | `COLUMNS` 有该列，且类型、长度、精度、标度、可空与目标一致 | 列不存在 |
| `modify_column` | 列的类型、长度、精度、标度、可空与任务目标一致 | 列仍是修改前的定义 |
| `drop_column` | 列不存在 | 列仍在 |
| `add_index` | `STATISTICS` 有该索引名，列序一致；全文索引还要 `INDEX_TYPE = 'FULLTEXT'` | 索引名不存在 |
| `drop_index` | 索引名不存在 | 索引仍在 |
| `create_junction` | 中间表存在，主键为 `(owner_id, target_id)` | 表不存在 |
| `drop_junction` | 中间表不存在 | 表仍在 |

列存在但定义既不是旧的也不是目标的：任务 `failed`，`error_text` 写明实际定义。这种状态只重试核对，不自动生成第三种 DDL。

进程在 `running` 期间崩溃时，重启后的执行器先拿命名锁，再按上表决定收尾或重跑。判断依据是定义，不是任务状态本身。

## 4. 多对多中间表

新增多对多只插入 `dm_link`、两侧 `dm_name` 和一条 `create_junction` 任务。中间表：

```sql
CREATE TABLE j_12 (
  owner_id   BIGINT UNSIGNED NOT NULL COMMENT 'owner 侧业务行 id',
  target_id  BIGINT UNSIGNED NOT NULL COMMENT 'target 侧业务行 id',
  created_at DATETIME(3)     NOT NULL COMMENT '建立关联的时间，UTC',
  PRIMARY KEY (owner_id, target_id),
  KEY idx_j_12_target (target_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '多对多中间表。物理名是 j_{linkId}，不软删除';
```

中间表不软删除。`unlink` 是物理删除中间行，不删除两端业务行。

加关联不建数据库外键。多对一只做 `ADD COLUMN`。一对一在同一次目录事务里排好列任务和唯一索引任务。多对多只建中间表。细节见 [元数据目录 6.2](01-元数据目录.md)。

## 5. 请求什么时候返回

目录事务提交是结构变更已经排队的完成点。DDL 在提交之后执行。

| 动作 | 请求行为 |
|---|---|
| `create_table`、可空 `add_column`、B 树 `add_index`、`drop_index` | 最多再等 3 秒 |
| `modify_column`、`drop_column`、`create_junction`、`drop_junction`、全文索引 | 提交后立即返回 202 |

3 秒内任务变为 `applied`：按该操作原来的成功码返回，正文带 `taskId` 和 `status = applied`。变为 `failed`：返回 500，正文带 `taskId`。仍是 `pending` 或 `running`：返回 202，正文带 `taskId`。执行器继续跑，不因为 HTTP 返回而取消 DDL。

调用方以任务或对象的 `status` 判断新列能否写入。响应不是 `applied` 时，数据 API 仍看不见该对象。

`ALTER TABLE` 会拿元数据锁，期间该表上的 DML 被堵住。数据连接把 `lock_wait_timeout` 设为 2 秒，超时返回 409，正文说明结构变更正在进行。不要把这段窗口实现成「已生效列仍可照常写入」。

全文索引的执行超时单独放宽，见 [全文索引](08-全文索引.md)。大表上的 `ADD FULLTEXT INDEX` 会重建索引，因此它总是 202。

## 6. 收紧列

把可空改为 `NOT NULL` 属于 `modify_column`。目录事务提交前检查：

1. 该列不存在 `NULL`。
2. 请求带 `confirm=true` 和 `minRevision`。
3. 应用已有 `published` 修订时，[实例心跳](09-多实例归属.md) 里每个 `seen_at` 在 15 秒内的 `api` 记录，其 `revision` 都大于等于 `minRevision`。没有新鲜心跳时返回 409，避免在无人上报的情况下收紧。
4. 应用从未发布源码时跳过第 3 步。

心跳落后时返回 409，正文列出仍停在旧修订的 `instance_id`。这次检查不过就不插入任务。

这个门闩覆盖的是已经打开的 `api` 进程。外部客户端仍可能漏传新字段，所以 `confirm=true` 保留。

## 7. 并发与核对

- 同一实体的可执行任务串行。不同实体可以并行。
- 提供管理用核对：比较某实体 `active` 字段与 `COLUMNS` 的类型、可空、精度；比较 `active` 索引与 `STATISTICS` 的列序和 `INDEX_TYPE`。只报告差异，不自动删列。
- 数据事务与结构任务互不嵌套。新列要等任务 `applied`。DDL 进行中，已有列上的写入可能得到 409。

## 8. 本模块完成标准

- 字段停用、清除、实体归档按目录模块的限制工作。失败任务可以安全重试；定义已经到位时重试只收口目录，不第二次执行 DDL。
- 一对一的唯一索引任务在列任务同一目录事务里出现。进程死在两步 DDL 之间时，重启后能放行 `blocked` 任务。
- `modify_column` 在列仍是旧定义时会重跑，在列已是新定义时不会把未完成的修改标成成功。
- `purge` 之外的结构操作，目录与 `information_schema` 核对无差异。
- `GET_LOCK` 与 DDL 发生在同一条数据库连接上。
