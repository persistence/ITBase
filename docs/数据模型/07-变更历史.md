# 变更历史

职责：业务行一旦新建、修改、删除，就在**同一 InnoDB 事务**里追加一条变更记录。提交成功后，异步任务按游标消费这些记录，做索引、通知、工作流之类的后续处理。

不负责：结构 DDL（见 [结构同步](02-结构同步.md)）；业务行本身的校验与 DML（见 [数据读写](04-数据读写.md)）；消费方的业务逻辑。

依赖：只由数据写入管线写入。HTTP 数据 API、解释器 `Create` / `Update` / `Delete` / `Tx`、以后的工作流，只要走该管线，都会留下历史。绕过管线的裸 SQL 不记，也不支持。

第一期所有业务实体都记，不在目录上做开关。结构任务、选项集、规则、源码发布不进入本表。

## 1. 为什么用一张 outbox，而不是 binlog 或 MQ

| 做法 | 与本方案的关系 |
|---|---|
| 业务表同事务写 `dm_record_change` | 采用。业务行提交了，历史一定在；业务回滚，历史也不在 |
| 听 MySQL binlog | 第一期不做。物理列名、软删除令牌、多对多中间表都要再解释一遍，和目录脱节 |
| 提交后再发 Kafka | 第一期不做。进程在提交后、发送前崩溃会丢事件。以后若要接 MQ，也从本表转发，不改写入路径 |
| 每个实体一张历史表 | 不采用。消费者无法用一条轮询覆盖全部实体，建实体还要多一次 DDL |

变更表是追加型。一行历史表示「某个实体的某一行，在一次写入里发生了一次 create / update / delete（或多对多的 link / unlink）」。一次请求里订单连带两行订单行，会留下三条历史，共用同一个 `write_id`。

## 2. 表

### 2.1 dm_record_change

```sql
CREATE TABLE dm_record_change (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  write_id      CHAR(26)        NOT NULL,
  seq           SMALLINT UNSIGNED NOT NULL,
  app_id        BIGINT UNSIGNED NOT NULL,
  app_code      VARCHAR(40)     NOT NULL,
  entity_id     BIGINT UNSIGNED NOT NULL,
  entity_code   VARCHAR(40)     NOT NULL,
  record_id     BIGINT UNSIGNED NOT NULL,
  op            VARCHAR(16)     NOT NULL,
  actor_id      BIGINT UNSIGNED NOT NULL,
  source        VARCHAR(16)     NOT NULL,
  before_json   JSON            NULL,
  after_json    JSON            NULL,
  created_at    DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_change_write_seq (write_id, seq),
  KEY idx_dm_change_entity_record (entity_id, record_id, id),
  KEY idx_dm_change_app (app_id, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`id` 单调递增，是消费游标的唯一依据。不要按 `created_at` 消费，时钟回拨会乱序。

`write_id` 是一次数据事务的 ULID，在 `BEGIN` 时生成。同一 `Tx` 回调里的多次 `Create` / `Update` 共用一个 `write_id`。事务外每次 `Create` / `Update` / `DELETE` 各自一个。

`seq` 从 0 起，按该事务里实际落库的顺序加，与 [数据读写 3.3](04-数据读写.md) 的写入顺序一致，方便消费者按图重放。

`op`：`create`、`update`、`delete`、`link`、`unlink`。

`source`：`api`（`/api/v1/data`）、`domain`（解释器领域函数）、`system`（平台内部以后用）。

`actor_id` 为当前登录用户。没有登录主体的系统调用使用 `0`，第一期数据 API 都要求登录，因此实际都是正整数。

`app_code`、`entity_code` 是写入当时目录里的副本。应用或实体以后改显示名不影响历史；编码本身不可改。

本表不更新、不按消费结果改状态。多消费者各自看游标表。

### 2.2 dm_change_consumer

```sql
CREATE TABLE dm_change_consumer (
  name          VARCHAR(40)     NOT NULL,
  last_id       BIGINT UNSIGNED NOT NULL DEFAULT 0,
  updated_at    DATETIME(3)     NOT NULL,
  PRIMARY KEY (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`name` 与编码规则相同：`^[a-z][a-z0-9_]{0,40}$`。一个名字一条游标，例如 `search_index`、`wf_trigger`。新消费者插入 `last_id = 0`，从头重放。

## 3. 何时写、写什么

校验通过并完成该行的 `INSERT` / `UPDATE` / 删除之后、`COMMIT` 之前插入历史。历史插入失败则整单回滚。不要在 `COMMIT` 之后补写。

只为**实际改动了存储**的对象写行：

| 写入图上的动作 | 历史 |
|---|---|
| 新建实体行 | 该实体 `create` |
| 更新 `values` 或改多对一 / 一对一外键 | 该实体 `update` |
| 软删除或物理删除实体行 | 该实体 `delete` |
| 一对多 `append` / `create` 子行 | 子实体 `create`，不是父行 `update` |
| 一对多 `update` 子行 | 子实体 `update` |
| 一对多 `remove` 子行 | 子实体 `delete` |
| 多对多 `link` / `unlink` | 在 **owner** 实体上记 `link` / `unlink`，`record_id` 为 owner 行 |
| `set` 外键但新旧 `id` 相同、`values` 也没变 | 不写 |
| 只读 | 不写 |

`before_json` / `after_json` 是该行自身的快照，不含一对多子树。形状：

```json
{
  "id": 41,
  "values": { "title": "PO-1", "amount": "12.50", "status": "open" },
  "refs": { "customer": 9 }
}
```

`values` 为当时全部 `active` 的标量、选项、文件字段，已按规则校验做过标准化。`refs` 只含落在本表上的多对一 / 一对一外键，值为目标 `id` 或 `null`。系统列不进 `values`；`id` 在外层。`file` 只存文件 id 数组。

| op | before_json | after_json |
|---|---|---|
| `create` | `null` | 新行快照 |
| `update` | 写入前快照 | 写入后快照 |
| `delete` | 删除前快照 | `null` |
| `link` | `null` | `{ "nav": "tags", "id": 5 }` |
| `unlink` | `{ "nav": "tags", "id": 5 }` | `null` |

`update` 存整行快照，不存字段差量。消费者若要差量，自己对 `before_json` 与 `after_json` 做键比较。

单条 JSON 序列化后超过 1MiB 则拒绝本次写入，返回 400。第一期不截断。

## 4. 写入管线里的位置

接在 [数据读写 3.3](04-数据读写.md) 第 7 步之后、`COMMIT` 之前：

1. 事务开始时生成 `write_id`。
2. 每成功插入、更新、删除一行（含软删除），立刻 `INSERT dm_record_change`，`seq` 加 1。
3. 多对多中间表插入或删除各记一条 `link` / `unlink`。
4. `COMMIT`。此后历史与业务行一起可见。
5. 提交成功后可向进程内通道发一个非可靠唤醒；消费者不以唤醒为正确性条件。

`Tx` 回滚时历史一起消失。CEL 失败、权限 403、唯一冲突都不会留下半条历史。

物理表名、JSON 键只用目录里的 `entity_code`、字段编码、导航编码，不写物理列名。字段停用后，旧历史仍保留当时快照；新写入不再包含 `retired` 字段。

## 5. 消费

平台起一组 goroutine，按消费者名字轮询。第一期不用独立进程，但协议按「可拆出去」来写：只认 `id` 游标，不认内存下标。

```text
SELECT *
FROM dm_record_change
WHERE id > :last_id
ORDER BY id
LIMIT 100
```

处理完一批后：

```text
UPDATE dm_change_consumer
SET last_id = :batch_max_id, updated_at = :now
WHERE name = :name AND last_id = :old_last_id
```

`last_id` 的 CAS 失败说明该名字有两个 worker 在跑。第一期每个 `name` 只允许一个 worker；CAS 失败则本次丢弃结果、重新读游标。

语义是至少一次。消费者必须按 `id` 幂等：搜索覆盖写、工作流用 `change.id` 做去重键。不要假设「同一 `record_id` 的 update 只会出现一次」。

同一 `write_id` 的多行可能被拆进相邻两批。需要整图的消费者应：读到某行后继续读到该 `write_id` 在本批之后没有更大 `seq` 为止；若下一条 `id` 仍是同一 `write_id`，先不提交游标，等下一批凑齐。更简单的做法是按行消费、不组图。第一期默认按行；要组图的消费者自己按 `write_id` 缓冲，缓冲超时 5 秒则按已到的 `seq` 处理并前进游标，避免卡死。

空转间隔 1 秒。被唤醒则立刻下一轮。单次处理超时 30 秒；超时视为失败，不前进游标，下轮重放同一批。

消费者进程内 panic 或 SQL 错误：不前进游标，记日志，退避后重试。不把失败行标成 dead letter 写回变更表。连续失败超过 50 次同一 `id` 时告警，仍停在该 `id`，避免跳过。

第一期内置消费者可以先只打日志，用来验证管线。流程以后按同样的 `name` 注册。库内全文检索不经过本表，见 [全文索引](08-全文索引.md)。消费者名 `search_index` 留给以后的外部搜索引擎。

## 6. 查询接口

给管理端和排查用，不是消费接口。消费禁止走 HTTP 再拉全表。

```text
GET /api/v1/data/apps/{appCode}/{entityCode}/{id}/changes?after=0&size=50
```

按 `id` 升序返回该行的历史。`after` 为上一页最后一条变更 `id`。`size` 默认 50，最大 200。不提供按时间倒序的筛选第一期可以后补。

响应：

```json
{
  "items": [
    {
      "id": 9001,
      "write_id": "01JB...",
      "seq": 0,
      "op": "update",
      "actor_id": 7,
      "source": "api",
      "before": { "id": 41, "values": { "status": "open" }, "refs": { "customer": 9 } },
      "after":  { "id": 41, "values": { "status": "confirmed" }, "refs": { "customer": 9 } },
      "created_at": "2026-11-03T08:00:00.000Z"
    }
  ]
}
```

无写权限的用户不能读历史。第一期与读该行详情使用同一读挂点。

## 7. 不做的事

- 不在变更表上存消费状态、重试次数、错误信息。
- 不因消费成功而删除历史。保留与清理以后单独立项；未立项前不自动删。
- 不记录 `GET` / `:query`。
- 不记录结构任务、字段停用、归档实体的目录变更。归档后的业务写入本身已被数据 API 拒绝，因此也不会有新历史。
- 第一期不做「只记某些字段」、字段级审计、变更对比 UI。
- 解释器不能直接 INSERT 本表。`itb` 不暴露变更 API；写业务行即可。

## 8. 本模块完成标准

- 一次 `POST` 新建订单、挂客户、建两行订单行，提交后 `dm_record_change` 有三条：订单 `create`、两行订单行 `create`，同一 `write_id`，`seq` 为 0,1,2。
- CEL 失败回滚后，业务表和变更表都没有新行。
- 解释器 `Tx` 里更新订单状态，历史 `source = domain`，`op = update`，`before_json` / `after_json` 能看出状态变化。
- 软删除订单产生 `op = delete`，`after_json` 为 `null`。
- 名为 `log` 的消费者能从 0 追上最新 `id`；重启后不重放已确认批次，崩溃后最多重复处理最后一批。
- 两个消费者名字互不影响游标。
