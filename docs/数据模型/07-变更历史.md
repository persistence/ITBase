# 变更历史

职责：业务行一旦新建、修改、删除，就在**同一 InnoDB 事务**里追加一条变更记录。提交成功后，异步任务按每个应用的 `visible_seq` 消费这些记录，做索引、通知、工作流之类的后续处理。

不负责：结构 DDL（见 [结构同步](02-结构同步.md)）；业务行本身的校验与 DML（见 [数据读写](04-数据读写.md)）；消费方的业务逻辑。谁持有消费租约见 [多实例归属](09-多实例归属.md)。

依赖：只由数据写入管线写入。HTTP 数据 API、解释器 `Create` / `Update` / `Delete` / `Tx`、以后的工作流，只要走该管线，都会留下历史。绕过管线的裸 SQL 不记，也不支持。

第一期所有业务实体都记，不在目录上做开关。结构任务、选项集、规则、源码发布不进入本表。

## 1. 为什么用一张 outbox，而不是 binlog 或 MQ

| 做法 | 与本方案的关系 |
|---|---|
| 业务表同事务写 `dm_record_change` | 采用。业务行提交了，历史一定在；业务回滚，历史也不在 |
| 用自增 `id` 当消费游标 | 不采用。`id` 在 `INSERT` 时分配，提交顺序可以相反。先看见较大 `id` 再把游标推过去，会永久跳过后提交的较小 `id`。回滚留下的空洞又不能一直等 |
| 听 MySQL binlog | 第一期不做。物理列名、软删除令牌、多对多中间表都要再解释一遍，和目录脱节 |
| 提交后再发 Kafka | 第一期不做。进程在提交后、发送前崩溃会丢事件。以后若要接 MQ，也从本表转发，不改写入路径 |
| 每个实体一张历史表 | 不采用。消费者无法用一条轮询覆盖全部实体，建实体还要多一次 DDL |

变更表是追加型。一行历史表示「某个实体的某一行，在一次写入里发生了一次 create / update / delete（或多对多的 link / unlink）」。一次请求里订单连带两行订单行，会留下三条历史，共用同一个 `write_id`。

消费顺序是每个应用内部的 `visible_seq`。不同应用之间没有全局顺序。

## 2. 表

### 2.1 dm_change_seq

```sql
CREATE TABLE dm_change_seq (
  app_id    BIGINT UNSIGNED NOT NULL COMMENT '应用主键。每个应用一行',
  next_seq  BIGINT UNSIGNED NOT NULL COMMENT '下一次要分配的 visible_seq，从 1 起。事务末尾加锁更新，持有到提交',
  PRIMARY KEY (app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '按应用分配变更序号';
```

每个应用一行。`next_seq` 从 1 起，表示下一次要分配的序号。应用创建时插入。缺失时，第一次数据事务里 `INSERT` 后再 `SELECT … FOR UPDATE`。

序号在事务**末尾**分配：业务行和变更行都写完之后，`SELECT next_seq … FOR UPDATE`，按本事务的 `seq` 从小到大填上 `visible_seq`，把 `next_seq` 加上本事务的条数，然后立刻 `COMMIT`。这把锁持有到提交或回滚。分配之后不许再写业务行。

锁住直到提交，提交顺序才和 `visible_seq` 一致。回滚会退回 `next_seq`，不留永久空洞。临界区只包住分配和提交，不包住前面的校验和业务写入。同一应用的提交在这行锁上排一下队；不同应用互不相干。

### 2.2 dm_record_change

```sql
CREATE TABLE dm_record_change (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '变更行主键。只给单行历史分页，禁止当作消费游标',
  app_id        BIGINT UNSIGNED NOT NULL COMMENT '所属应用',
  visible_seq   BIGINT UNSIGNED NULL COMMENT '应用内消费序号。插入时为空，提交前填上。已提交的行一定有值',
  write_id      CHAR(26)        NOT NULL COMMENT '一次数据事务的 ULID',
  seq           SMALLINT UNSIGNED NOT NULL COMMENT '该事务内的落库顺序，从 0 起',
  app_code      VARCHAR(40)     NOT NULL COMMENT '写入当时的应用编码副本',
  entity_id     BIGINT UNSIGNED NOT NULL COMMENT '实体 id',
  entity_code   VARCHAR(40)     NOT NULL COMMENT '写入当时的实体编码副本',
  record_id     BIGINT UNSIGNED NOT NULL COMMENT '业务行 id。link 与 unlink 记 owner 行',
  op            VARCHAR(16)     NOT NULL COMMENT 'create、update、delete、link、unlink',
  actor_id      BIGINT UNSIGNED NOT NULL COMMENT '操作者用户 id。无登录主体时为 0',
  source        VARCHAR(16)     NOT NULL COMMENT 'api、domain、system',
  before_json   JSON            NULL COMMENT '写入前快照。不含 text、json、file 原文',
  after_json    JSON            NULL COMMENT '写入后快照。不含 text、json、file 原文',
  created_at    DATETIME(3)     NOT NULL COMMENT '写入时间，UTC。消费不按它排序',
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_change_app_seq (app_id, visible_seq),
  UNIQUE KEY uk_dm_change_write_seq (write_id, seq),
  KEY idx_dm_change_entity_record (entity_id, record_id, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '业务行变更。与业务 DML 同一事务，只追加';
```

`id` 只给单行历史分页。消费禁止用 `id` 做游标。

`visible_seq` 在插入变更行时为空，提交前填上。已提交的行一定有序号。唯一键允许多个空值，未提交的行互不影响。消费者只查询 `visible_seq IS NOT NULL`。

`write_id` 是一次数据事务的 ULID，在 `BEGIN` 时生成。同一 `Tx` 回调里的多次 `Create` / `Update` 共用一个 `write_id`。事务外每次 `Create` / `Update` / `DELETE` 各自一个。

`seq` 从 0 起，按该事务里实际落库的顺序加，与 [数据读写 3.3](04-数据读写.md) 的写入顺序一致。`visible_seq` 按这个 `seq` 递增分配。

`op`：`create`、`update`、`delete`、`link`、`unlink`。

`source`：`api`（`/api/v1/data`）、`domain`（解释器领域函数）、`system`（平台内部以后用）。

`actor_id` 为当前登录用户。没有登录主体的系统调用使用 `0`，第一期数据 API 都要求登录，因此实际都是正整数。

`app_code`、`entity_code` 是写入当时目录里的副本。应用或实体以后改显示名不影响历史；编码本身不可改。

本表不更新、不按消费结果改状态。多消费者各自看游标表。

### 2.3 dm_change_consumer

```sql
CREATE TABLE dm_change_consumer (
  name          VARCHAR(40)     NOT NULL COMMENT '消费者名字，如 log、wf_trigger',
  app_id        BIGINT UNSIGNED NOT NULL COMMENT '应用。同一名字在每个应用上各有一条游标',
  last_seq      BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '已确认的最大 visible_seq',
  updated_at    DATETIME(3)     NOT NULL COMMENT '游标更新时间，UTC',
  PRIMARY KEY (name, app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '变更消费进度。不记录谁正在跑';
```

`name` 与编码规则相同：`^[a-z][a-z0-9_]{0,39}$`。同一个名字在每个应用上有一条游标，例如 `log`、`wf_trigger`。新消费者从 `last_seq = 0` 起，只能读到尚未清理的行。要重建外部索引时应扫业务表，而不是依赖已经删掉的历史。

## 3. 何时写、写什么

校验通过并完成该行的 `INSERT` / `UPDATE` / 删除之后、分配 `visible_seq` 之前插入历史。历史插入失败则整单回滚。不要在 `COMMIT` 之后补写。

只为**实际改动了存储**的对象写行：

| 写入图上的动作 | 历史 |
|---|---|
| 新建实体行 | 该实体 `create` |
| 更新 `values` 或改多对一 / 一对一外键 | 该实体 `update` |
| 软删除或物理删除实体行 | 该实体 `delete` |
| 一对多 `append` / `create` 子行 | 子实体 `create`，不是父行 `update` |
| 一对多 `update` 子行 | 子实体 `update` |
| 一对多 `remove` 子行 | 子实体 `delete` |
| 多对多 `link` / `unlink` | 在 **owner** 实体上记 `link` / `unlink`，`record_id` 为 owner 行。owner 的 `updated_at` 与 `row_version` 会变，但不另写一条 `update` |
| `set` 外键但新旧 `id` 相同、`values` 也没变 | 不写 |
| 只读 | 不写 |

`before_json` / `after_json` 是该行自身的快照，不含一对多子树。形状：

```json
{
  "id": "41",
  "rowVersion": "4",
  "values": { "title": "PO-1", "amount": "12.50", "status": "open" },
  "refs": { "customer": "9" },
  "omitted": ["body", "attachments"]
}
```

`values` 为当时全部 `active` 的标量与选项，已按规则校验做过标准化。`text`、`json`、`file` 不写入快照原文，编码列在 `omitted`。消费者要正文时回读业务行；物理删除之后正文不在历史里，第一期接受这一点。`refs` 只含落在本表上的多对一 / 一对一外键，值为目标 id 的十进制字符串或 `null`。系统列里只有 `id` 和 `rowVersion` 出现在快照外层。

| op | before_json | after_json |
|---|---|---|
| `create` | `null` | 新行快照 |
| `update` | 写入前快照 | 写入后快照 |
| `delete` | 删除前快照 | `null` |
| `link` | `null` | `{ "nav": "tags", "id": "5" }` |
| `unlink` | `{ "nav": "tags", "id": "5" }` | `null` |

`update` 存整行快照，不存字段差量。消费者若要差量，自己对 `before_json` 与 `after_json` 做键比较。

去掉 `omitted` 字段之后，单条 JSON 仍超过 1MiB 则拒绝本次写入，返回 400。第一期不截断。

保留 90 天。清理只删除同时满足两点的行：`created_at` 早于当前 UTC 90 天，且该 `app_id` 上每个已登记消费者的 `last_seq` 都已经大于等于这行的 `visible_seq`。没有登记任何消费者时，仍删除 90 天前的行。清理不改游标。

## 4. 写入管线里的位置

接在 [数据读写 3.3](04-数据读写.md) 第 7 步之后、`COMMIT` 之前：

1. 事务开始时生成 `write_id`。
2. 每成功插入、更新、删除一行（含软删除），立刻 `INSERT dm_record_change`，`visible_seq` 为空，`seq` 加 1。
3. 多对多中间表插入或删除各记一条 `link` / `unlink`。
4. 锁 `dm_change_seq`，填上 `visible_seq`。
5. `COMMIT`。此后历史与业务行一起可见。
6. 提交成功后可向进程内通道发一个非可靠唤醒；消费者不以唤醒为正确性条件。

`Tx` 回滚时历史和序号一起消失。CEL 失败、权限 403、唯一冲突都不会留下半条历史。

物理表名、JSON 键只用目录里的 `entity_code`、字段编码、导航编码，不写物理列名。字段停用后，旧历史仍保留当时快照；新写入不再包含 `retired` 字段。

## 5. 消费

只有 `worker`（或本地 `all`）进程在**持有该名字的租约**之后才轮询。`api` 副本不消费。租约表与抢主见 [多实例归属](09-多实例归属.md)。协议只认 `(app_id, visible_seq)`，不认 `id`，也不认内存下标。

对每个有未消费数据的应用：

```text
SELECT *
FROM dm_record_change
WHERE app_id = :app_id
  AND visible_seq > :last_seq
ORDER BY visible_seq
LIMIT 100
```

处理完一批后：

```text
UPDATE dm_change_consumer
SET last_seq = :batch_max_seq, updated_at = :now
WHERE name = :name AND app_id = :app_id AND last_seq = :old_last_seq
```

`last_seq` 的 CAS 失败说明该名字有两个 worker 在跑。第一期每个 `name` 只允许一个 worker；CAS 失败则本次丢弃结果、重新读游标，不把副作用再做一遍的责任推给游标本身。副作用仍可能在租约过期的窗口里发生两次，所以消费者按 `visible_seq` 幂等。

续约必须在批处理期间并行进行。续约失败就取消本批，并且不许推进 `last_seq`。处理超时 30 秒大于租约 15 秒，不能等这一批做完再续约。

语义是至少一次。消费者必须按 `visible_seq` 幂等：搜索覆盖写、工作流用 `app_id + visible_seq` 做去重键。不要假设「同一 `record_id` 的 update 只会出现一次」。

同一 `write_id` 的多行序号连续，但仍可能被拆进相邻两批。需要整图的消费者应：读到某行后继续读到该 `write_id` 在本批之后没有更大 `seq` 为止；若下一条仍是同一 `write_id`，先不提交游标，等下一批凑齐。更简单的做法是按行消费、不组图。第一期默认按行；要组图的消费者自己按 `write_id` 缓冲，缓冲超时 5 秒则按已到的 `seq` 处理并前进游标，避免卡死。

空转间隔 1 秒。被唤醒则立刻下一轮。单次处理超时 30 秒；超时视为失败，不前进游标，下轮重放同一批。

消费者进程内 panic 或 SQL 错误：不前进游标，记日志，退避后重试。不把失败行标成 dead letter 写回变更表。连续失败超过 50 次同一 `visible_seq` 时告警，仍停在该序号，避免跳过。

第一期内置消费者可以先只打日志，用来验证管线。流程以后按同样的 `name` 注册。库内全文检索不经过本表，见 [全文索引](08-全文索引.md)。消费者名 `search_index` 留给以后的外部搜索引擎。

## 6. 查询接口

给管理端和排查用，不是消费接口。消费禁止走 HTTP 再拉全表。

```text
GET /api/v1/data/apps/{appCode}/{entityCode}/{id}/changes?after=0&size=50
```

按 `id` 升序返回该行的历史。`after` 为上一页最后一条变更 `id`。`size` 默认 50，最大 200。这里的 `id` 是变更行主键，不是 `visible_seq`。

响应：

```json
{
  "items": [
    {
      "id": "9001",
      "visibleSeq": "120",
      "writeId": "01JB...",
      "seq": 0,
      "op": "update",
      "actorId": "7",
      "source": "api",
      "before": { "id": "41", "rowVersion": "3", "values": { "status": "open" }, "refs": { "customer": "9" } },
      "after":  { "id": "41", "rowVersion": "4", "values": { "status": "confirmed" }, "refs": { "customer": "9" } },
      "createdAt": "2026-11-03T08:00:00.000Z"
    }
  ]
}
```

无写权限的用户不能读历史。第一期与读该行详情使用同一读挂点。

## 7. 不做的事

- 不在变更表上存消费状态、重试次数、错误信息。
- 不因消费成功而删除历史。过期清理只按第 3 节的 90 天规则，不按「已经被某个消费者看见」。
- 不记录 `GET` / `:query`。
- 不记录结构任务、字段停用、归档实体的目录变更。归档后的业务写入本身已被数据 API 拒绝，因此也不会有新历史。
- 第一期不做「只记某些字段」、字段级审计、变更对比 UI。
- 解释器不能直接 INSERT 本表。`itb` 不暴露变更 API；写业务行即可。
- 不提供跨应用的单一递增游标。

## 8. 本模块完成标准

- 一次 `POST` 新建订单、挂客户、建两行订单行，提交后 `dm_record_change` 有三条：订单 `create`、两行订单行 `create`，同一 `write_id`，`seq` 为 0,1,2，`visible_seq` 连续。
- 两个事务并发时，后提交的那个拿到更大的 `visible_seq`。消费者按序号前进，不会跳过先分配 id、后提交的事务。
- CEL 失败回滚后，业务表、变更表和 `next_seq` 都没有留下这次写入。
- 解释器 `Tx` 里更新订单状态，历史 `source = domain`，`op = update`，`before_json` / `after_json` 能看出状态变化。快照不含 `text` 原文。
- 软删除订单产生 `op = delete`，`after_json` 为 `null`。
- 名为 `log` 的消费者能从 0 追上该应用最新 `visible_seq`；重启后不重放已确认批次，崩溃后最多重复处理最后一批。
- 两个消费者名字互不影响游标。同一名字在两个应用上的 `last_seq` 互不影响。
