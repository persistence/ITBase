# 数据读写

职责：按目录读写业务记录。写接口在同一个 InnoDB 事务里改当前表和关联表。读接口按主实体分页，再用批量查询补关联，不把一对多 JOIN 进列表。

不负责：登记实体和结构（见 [元数据目录](01-元数据目录.md)）；跑 DDL（见 [结构同步](02-结构同步.md)）；CEL 环境与白名单（见 [规则校验](03-规则校验.md)，本模块按顺序调用它）。

依赖：只使用 `active` 的字段和关联。物理表名只从目录读取，不拼接调用方传来的任意字符串。归档实体拒绝读写。

前缀 `/api/v1/data`。解释器里的 `itb.App` 走同一条管线，见 [解释器运行时](06-解释器运行时.md)。

## 1. 接口

实体编码在应用内查找，路径里带 `appCode`。

```text
POST   /apps/{appCode}/{entityCode}
PATCH  /apps/{appCode}/{entityCode}/{id}
DELETE /apps/{appCode}/{entityCode}/{id}

GET    /apps/{appCode}/{entityCode}/{id}
POST   /apps/{appCode}/{entityCode}:query
```

| 方法 | 作用 | 成功 |
|---|---|---|
| `POST /{entityCode}` | 新建根行，并可在同一事务里写关联 | 201，正文为根行记录 |
| `PATCH /{entityCode}/{id}` | 更新根行及关联 | 200，正文为本次写过的那棵图 |
| `DELETE /{entityCode}/{id}` | 按实体的软删除规则删除根行 | 204，无正文 |
| `GET /{entityCode}/{id}` | 读一行，`expand` 展开导航 | 200；不存在或已删除为 404 |
| `POST /{entityCode}:query` | 列表：筛选、排序、分页、展开 | 200，正文为 `items` + `page` |

第一期不提供批量删除、批量更新、物理恢复、列表深展开一对多。`GET /{entityCode}` 不作为列表入口，避免把条件树塞进查询串。

`itb.App` 的对应关系：`Create` / `Update` / `Delete` / `Read` / `Query` 分别进入上表五条路径。`Query` 的条件构造函数与 `:query` 的 `filter` 同源。

## 2. 记录形状

读写使用同一形状。`id` 与审计列在外层，`values` 只含当前实体的标量、选项、文件字段。关联一律在 `links` 里。未展开的导航不出现。

```json
{
  "id": "41",
  "rowVersion": "3",
  "created_at": "2026-11-01T14:00:00.000Z",
  "updated_at": "2026-11-01T14:00:00.000Z",
  "created_by": "1",
  "updated_by": "1",
  "values": { "title": "PO-1", "amount": "12.50", "qty": 2 },
  "links": {
    "customer": { "id": "9", "title": "Acme" },
    "lines": [
      { "id": "7", "rowVersion": "1", "values": { "sku": "A", "qty": 2 } }
    ]
  }
}
```

`id`、`rowVersion`、`created_by`、`updated_by` 以及关联里的 `id` 都是十进制字符串。`values` 里的 `bigint` 同样是字符串；`int` 仍是 JSON 数字。请求若用 JSON 数字表达 `BIGINT`，返回 400。

关联上的 `title` 来自目标实体的 `title_field`。目标没有标题字段时，多对一 / 一对一只返回 `id`。`values` 不接受系统字段键。`created_by` / `updated_by` 来自当前登录用户，请求体里的同名键忽略。

列表响应：

```json
{
  "items": [ { "id": "41", "rowVersion": "3", "values": { "title": "PO-1" }, "links": { "customer": { "id": "9", "title": "Acme" } } } ],
  "page": { "number": 1, "size": 20, "total": 136 }
}
```

`total` 是主实体去重后的行数，不是 JOIN 之后的行数。

## 3. 写入

### 3.1 请求体

```json
{
  "rowVersion": "3",
  "values": {
    "title": "PO-1",
    "amount": "12.50"
  },
  "links": {
    "customer": { "op": "set", "id": "9" },
    "lines": {
      "op": "append",
      "items": [
        {
          "values": { "sku": "A", "qty": 2 },
          "links": { "product": { "op": "set", "id": "3" } }
        }
      ]
    }
  }
}
```

`POST` 不带 `rowVersion`。`PATCH` 必须带根行当前的 `rowVersion`。子行 `update` 的每个元素再带该子行的 `rowVersion`。

`PATCH` 只更新出现在 `values` 里的键，未出现的列保持原值。要清空可空标量，显式传 JSON `null`。交给 CEL 的 `record` 是合并之后的整行，见 [规则校验](03-规则校验.md)。

### 3.2 操作与关联种类

| op | 适用 | 行为 |
|---|---|---|
| `set` | 多对一、一对一 | 把外键改成已存在的 `id`；`id` 为 `null` 时清空，列不可空则拒绝 |
| `create` | 多对一、一对一、一对多 | 插入关联行。一对多时把新行的外键设为当前行 |
| `update` | 一对多、多对一已存在的目标 | 按 `id` 和 `rowVersion` 更新该行的 `values` 与更深层 `links` |
| `remove` | 一对多 | 按该实体的软删除规则删除子行 |
| `append` | 一对多 | 在已有子行之外再 `create` 若干行，不删除未点名的子行 |
| `link` | 多对多 | 插入中间表，两端行必须已存在 |
| `unlink` | 多对多 | 删除中间表对应行 |

`create` 的元素可以继续带 `links`。从一个根行算起，嵌套深度最多 3。一次请求最多 100 个写节点。图里不允许出现环。

第一期不提供「用一份列表替换全部子行」。调用方明确使用 `append`、`update`、`remove`。

`set` 与 `link` 不创建目标行，避免一次保存意外插入主数据。要新建目标，使用 `create`。

### 3.3 事务内的写入顺序

1. 解析整张图，核对导航种类与 `op` 是否匹配。`BIGINT` 字段拒绝 JSON 数字。
2. `BEGIN`。隔离级别 `REPEATABLE READ`。
3. 先写根行。根行是新建时，子行要等根行 `id` 出来后再写外键。更新根行时 `UPDATE … WHERE id = ? AND deleted_token = 0 AND row_version = ?`。影响行数为 0 则再读该行：无未删除行返回 404，版本不同返回 409。
4. 多对一的 `create`：先插入目标行，再把目标 `id` 回填到当前行外键并更新。若当前行也是本次新建，则在 `INSERT` 时直接写入该外键，避免多一次更新。
5. 一对多的 `create` / `append`：插入子行，外键列为根行 `id`。
6. 多对多在两端 `id` 都确定后写中间表。`link` 与 `unlink` 若实际改变了成员，把 owner 行的 `updated_at`、`updated_by` 更新，并让 owner 的 `row_version` 加 1。这一下不算第二条实体 `update` 历史，成员变化由 `link` / `unlink` 历史表达。
7. 每插入或更新一行之前，跑完 [规则校验第 4 节](03-规则校验.md) 的顺序。`server` 规则能看见本事务里已经写入的行。提交前不复查整图。
8. 该行（以及多对多中间表的插入或删除）一旦真正改到存储，立刻写入 [变更历史](07-变更历史.md)，此时 `visible_seq` 仍为空。历史失败则整单回滚。
9. 业务写完后锁住本应用的 `dm_change_seq`，按 `seq` 分配 `visible_seq`，然后 `COMMIT`。分配之后不许再写业务行。失败则 `ROLLBACK`，不留下半张订单，也不留下历史。

同一行在这次事务里只把 `row_version` 加 1。没有任何存储变化时不加版本，也不写历史。

数据事务与结构任务互不嵌套。新列要等任务 `applied`。DDL 持有元数据锁时，本事务的 DML 最多等待 `lock_wait_timeout = 2` 秒，超时回滚并返回 409。

写入成功的响应形状与带相同 `expand` 的 `GET` 一致，只包含本次请求写过的节点。

### 3.4 删除

`DELETE /apps/{appCode}/{entityCode}/{id}?rowVersion=3` 只删根行，不级联删关联实体。缺少 `rowVersion` 返回 400。版本不匹配返回 409。中间表行在根行软删除后仍可能存在，列表默认带 `deleted_token = 0`，已删根行不会再被查到；以后若要清中间表，单独立项。

`soft_delete = 1`：把 `deleted_at` 写成当前 UTC，把 `deleted_token` 写成该行 `id`，并把 `row_version` 加 1。`soft_delete = 0`：物理 `DELETE`。一对多的 `remove` 遵守子实体自己的这个开关，并带上子行的 `rowVersion`。

删除前走写权限挂点。不跑 CEL。不能删除某种状态的行，由领域函数在调用删除前判断；通用删除接口本身没有这条规则。目标不存在或已删除返回 404。

## 4. 读取

列表和详情共用目录、共用 `active` 字段、共用记录形状。列表的执行计划与详情不同：详情按一个 `id` 取根行再展开；列表先在主实体上筛出一页 id，再批量补关联。

第一期读路径不写 JOIN。主查询的 `FROM` 只有当前实体表。跨实体筛选用 `IN (SELECT …)` 子查询。关联展示在主查询分页完成之后，用 `id IN (…)` 批量加载。

### 4.1 详情

```text
GET /apps/{appCode}/{entityCode}/{id}?expand=customer,lines
```

`expand` 为导航编码列表，逗号分隔，最多 8 个，必须是该实体上 `active` 的导航。重复编码忽略。未知导航返回 400。

展开规则：

| 导航种类 | 详情 | 列表 |
|---|---|---|
| 多对一、一对一 | 允许，补 `id` 与 `title`；需要目标行 `values` 时该导航仍只返回摘要，不自动再展开下一层 | 允许，同样只补摘要 |
| 一对多 | 允许，子行默认最多 50，按 `id` 升序；超出截断，不另报总数 | 拒绝 |
| 多对多 | 允许，对端摘要最多 50 | 拒绝 |

第一期 `expand` 只作用于根行的直接导航，不支持 `lines.product` 这种第二层路径。要读子行上的关联，先 `GET` 子实体。

一对多、多对多在详情里超出 50 的部分丢弃。调用方需要完整子表时，对子实体做 `:query`，条件为主键外键等于当前 `id`。

### 4.2 列表请求

```json
{
  "filter": {
    "and": [
      { "field": "status", "op": "eq", "value": "open" },
      { "field": "amount", "op": "gte", "value": "100.00" },
      { "field": "customer.city", "op": "eq", "value": "上海" }
    ]
  },
  "sort": { "field": "created_at", "dir": "desc" },
  "page": 1,
  "size": 20,
  "expand": ["customer"]
}
```

| 字段 | 约束 |
|---|---|
| `filter` | 可空。空表示只加软删除与权限条件 |
| `search` | 可空。按当前实体的一条 `active` 全文索引检索，与 `filter` 同时成立。字段、改写和 `MATCH` 见 [全文索引](08-全文索引.md) |
| `sort` | 可空。未带 `search` 时默认 `{ "field": "id", "dir": "desc" }`。带 `search` 且未指定 `sort` 时按相关度降序，再用 `id` 降序。指定了 `sort` 时只能是当前实体的一个 `active` 字段或 `id` / `created_at` / `updated_at`。`dir` 为 `asc` 或 `desc` |
| `page` | 从 1 起，默认 1 |
| `size` | 默认 20，最大 200 |
| `expand` | 最多 8 个导航。列表只允许多对一、一对一 |

条件树深度最多 3，叶子最多 20。`and` / `or` 的子项至少 1 个、最多 10 个。

叶子：

```json
{ "field": "amount", "op": "gte", "value": "100.00" }
```

`field` 是当前实体字段编码，或一层导航路径 `navCode.fieldCode`。路径里的导航必须 `active`。目标字段必须是可筛选类型：`string`、`int`、`bigint`、`decimal`、`bool`、`date`、`datetime`、`option`、`id`。`text`、`json`、`file`、`ref` 不能出现在 `field` 上；`ref` 用导航路径表达。

| op | 适用 | `value` |
|---|---|---|
| `eq` `ne` | 可筛选类型 | 单值，类型与字段一致 |
| `gt` `gte` `lt` `lte` | `int` `bigint` `decimal` `date` `datetime` `string` | 单值 |
| `in` | 可筛选类型 | 数组，1–100 个元素 |
| `contains` `startsWith` `endsWith` | `string` `option` | 字符串，长度 1–80 |
| `isNull` | 可筛选类型 | JSON 布尔 |

`decimal`、`bigint` 和 `id` 的比较值用十进制字符串。字符串比较前按规则校验里的规则去掉首尾空白。空字符串视为 `null`，与 `eq` 空串一起写成 `isNull: true`。

### 4.3 列表执行计划

分两段，对应两种需求：**筛出这一页主行**，**给这些主行补关联展示**。

1. 解析 `filter`，拆成「当前表谓词」和「一层导航谓词」。未知字段、未知导航、类型不匹配、列表里展开一对多，直接 400。`search.index` 不是当前实体的 `active` 全文索引时同样 400。
2. 读之前挂上权限模块给出的主表谓词。最终 `WHERE` 是 `权限谓词 AND 软删除条件 AND (用户 filter)`。权限谓词包在用户条件外面，用户 filter 里的 `or` 不能放宽数据范围。实体关闭软删除则不加 `deleted_token = 0`。
3. 当前表谓词直接进入主查询。带 `search` 时，把该全文索引的 `MATCH` 用 `AND` 接上，列顺序与改写见 [全文索引](08-全文索引.md)。未指定 `sort` 时 `ORDER BY` 改为相关度降序、`id` 降序。
4. 导航谓词生成参数化子查询，仍然只查询主表行：
   - 多对一 / 一对一：`主表.fk IN (SELECT id FROM 目标表 WHERE … AND deleted_token = 0)`
   - 一对多：`主表.id IN (SELECT 子表.fk FROM 子表 WHERE … AND deleted_token = 0)`
   - 多对多：`主表.id IN (SELECT owner_id FROM 中间表 WHERE target_id IN (SELECT id FROM 对端 WHERE …))`
5. `SELECT` 主表当前页。已指定 `sort`，或请求未带 `search` 时，`ORDER BY` 只使用主表列。`LIMIT` / `OFFSET` 按 `page`、`size`。并行 `COUNT(*)` 使用同一组 `WHERE`（含 `MATCH`），不加 `ORDER BY`。
6. 若 `expand` 非空：从本页主行收集外键，对每个导航一次 `id IN (…)` 批量加载目标行，在内存里填 `links`。目标行同样加软删除条件和读权限；无权或已删除则该导航为 `null`，不 404 整页。
7. 组装 `items`。列表的 `values` 含 `active` 的标量与选项，但省略 `text`、`json`、`file`。详情含这三类。不另提供字段投影；要看正文时 `GET` 该行，或对 `text` 使用全文索引。

不采用的做法：把关联表 JOIN 进主查询再分页。一对多、多对多会放大行数，`total` 和页码都会错。也不在应用进程里先拉出全部关联 id 再 `IN` 主表，以免条件命中过大时撑爆内存；子查询把集合留在 MySQL。

解释器 `Query` 使用同一计划。领域函数若还要关联展示，传与 HTTP 相同的 `expand`；需要一对多完整子表时，再对子实体 `Query`。

### 4.4 查询参数化

列名、表名、导航到物理列的映射只来自目录。`op` 映射成固定 SQL 片段。用户输入只出现在绑定参数里。

`contains` 使用 `LIKE`，参数两侧由服务端加 `%`，并对 `\`、`%`、`_` 转义。禁止把调用方字符串拼进 `LIKE` 模板。全文检索走 `search`，不把 `contains` 改写成 `MATCH`。

`OFFSET` 超过 10000 时返回 400，第一期不做键集分页。深翻页以后单独立项。

## 5. 和权限、流程的边界

目录不存角色、数据范围、节点和页面。

数据 API 留两个挂点，第一期可以先放行，接 Cerbos 时不改表结构：

- 写之前：按实体、字段、关联判断当前用户能否写这些键。未知字段先返回 400。已知但无写权限的键返回 403，不进入校验。
- 读之前：按数据范围给出主查询谓词，数据 API 把它 AND 到用户 filter 外面。范围条件由权限模块生成，数据 API 只接收已解析的谓词，不接收 SQL 字符串。`expand` 加载目标行时用目标实体的读范围再滤一次。

工作流要写业务表时，调用同一套数据 API，不直接 `INSERT` 物理表。这样 CEL、外键和事务顺序只有一条路径。工作流以后要执行业务动作时，调用已发布的领域函数，见 [源码与发布](05-源码与发布.md)。

## 6. 错误

| HTTP | 何时 |
|---|---|
| 400 | 未知字段或导航、`op` 与类型不符、条件树超限、列表 `expand` 了一对多、`OFFSET` 过深 |
| 401 | 未登录 |
| 403 | 权限挂点拒绝 |
| 404 | 根行不存在或已删除；归档实体 |
| 409 | 唯一索引冲突；`rowVersion` 不匹配；实体仍是 `pending` 或 `failed`；DDL 占着该表的元数据锁 |
| 422 | 必填、长度、选项、外键、CEL 失败。正文列出 `entityCode`、行临时键、`ruleCode` 或约束名、`message` |

## 7. 本模块完成标准

- 五条接口可用：新建、更新、删除、详情、列表。
- 一次 `POST` 能新建订单、挂上已有客户、并新建订单行；中途任意规则失败时，三处都不留新行。
- 读写响应形状一致；详情 `expand` 可含一对多，列表 `expand` 只能是多对一 / 一对一。
- `:query` 在主表上分页；`customer.city` 这类一层路径用子查询过滤，不 JOIN 主查询。带 `search` 时，全文条件与 `filter`、软删除、读权限同时生效。列表项不含 `text`、`json`、`file`。
- 两个并发 `PATCH` 带同一个 `rowVersion` 时，只有一个成功，另一个 409。`link` 成功后 owner 的 `updated_at` 变化。
- 带 `expand=customer` 的列表对本页外键只打一次批量查询。
- 权限挂点位置固定：写之前 403，读之前追加主表范围条件。
