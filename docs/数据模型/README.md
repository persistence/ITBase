# 数据模型

产品名称用「数据模型」。代码里一类业务数据叫实体 `entity`，实体上的一项属性叫字段 `field`，实体之间可导航的连接叫关联 `link`。描述这些结构的数据在文档里称目录。

实现栈：Go、GoFrame、MySQL 8、cel-go、Yaegi。组织是单组织、多应用。实体归属某个应用。

本目录合并原 v1 结构方案与 v1.1 应用代码方案，按实现模块拆开。阅读顺序与落地顺序相同：先内核，后扩展。

## 要落地的能力

1. 用 API 增加、修改、删除实体和结构，并让 MySQL 物理表跟上目录。
2. 校验规则用 CEL 文本保存。服务端用 cel-go 执行，前端执行同一段文本。
3. 一次数据 API 在同一个数据库事务里写入当前表和关联表。
4. 用 Yaegi 解释执行应用代码，增加领域函数和新的 HTTP 接口；实体、字段、关联、CEL、物理表仍由前三项负责。

## 三份数据

| 份 | 存在哪 | 谁写入 | 谁读取 |
|---|---|---|---|
| 目录 | `dm_*` 表 | 结构 API、源码发布 API | 结构 API、数据 API、管理后台、解释器宿主 |
| 物理表 | `information_schema` 里的业务表 | 结构执行器跑 DDL | 数据 API |
| 业务记录 | 各实体物理表、多对多中间表 | 数据 API（含解释器经宿主调用的同一条管线） | 数据 API |
| 变更历史 | `dm_record_change` | 数据写入管线，与业务 DML 同一事务 | 异步消费者、历史查询接口 |

目录是目标结构。物理表是已经执行成功的结构。两者允许短暂不一致：实体或字段处于 `pending` 或 `failed` 时，数据 API 看不见它。

页面、审批、工作流、权限不写入目录。它们只引用已经生效的 `entityCode`、`fieldCode`、`linkCode`。工作流要写业务表或执行业务动作时，调用数据 API 或已发布的领域函数，不直接 `INSERT` 物理表。

## 原则

- 编码创建后不改。显示名可以改。物理表名、物理列名在创建时定死，之后不随显示名变化。编码最长 40，表名 `appCode__entityCode` 最长 64，超长直接拒绝。
- 结构 API 先提交目录和结构任务，再在事务外执行 DDL。MySQL 的 `ALTER TABLE` 会隐式提交当前事务，不能把目录更新和 DDL 放进同一个事务。同一实体上的后续任务在这次目录事务里写成 `blocked`，不许等前一步成功后再插入。
- DDL 是否已经生效，以 `information_schema` 里的类型、可空、精度和索引定义为准，不以「列名还在不在」为准。
- 数据写入只使用状态为 `active` 的字段和关联，并且全部 DML 放在一个 InnoDB 事务里。`ALTER` 持有元数据锁期间，数据写入会等待一小段时间后返回 409，不把这段窗口说成仍可写入。
- 收紧列（可空改为必填）之前，该列不能有 `NULL`，并且各 `api` 进程心跳上的已装载修订都已经达到请求声明的修订。顺序是：先加可空列，再发布会写它的代码，最后收紧。
- 关联是独立对象，不把「一对多」做成当前表上的一个列。当前表上只为「多对一 / 一对一」放外键列。引用列编码占用字段名；反向导航只占用导航名。名字由 `dm_name` 保证唯一。
- CEL 只做单行布尔规则。必填、类型、长度、唯一由目录和数据库约束负责。跨行不变量用唯一索引，或领域函数里的锁定读。`PATCH` 送给规则的是合并后的整行。
- 能在浏览器里跑的规则，和必须读库的规则分开存。保存规则时就拒绝前端跑不了的写法。`matches` 两端都按 RE2。
- 解释器拿不到 `*gdb.DB`、SQL 字符串、DDL、标准库 `os` / `net`。领域函数里的每次写入都走数据读写模块，写不出绕过 CEL 的插入。应用代码的作者视为本组织的可信开发者。
- 变更消费按每个应用的 `visible_seq`。这个序号在事务末尾、持锁直到提交时分配。自增 `id` 只给单行历史分页。
- JSON 里的 `BIGINT`、记录 `id`、外键和 `rowVersion` 都是十进制字符串。`INT` 仍是 JSON 数字。

## 第一期做完的标准

目录、结构、校验、数据：

- 能通过 API 创建应用内实体，增加规定种类的字段，增加多对一、一对一、一对多导航和多对多，增加唯一索引、普通索引，以及 `string` / `text` 上的单列或联合全文索引。
- 字段停用、清除、实体归档按结构同步里的限制工作。失败任务可以安全重试。一对一的列任务和唯一索引任务在同一次目录事务里排队。崩溃后按列定义核对，不会把未改完的列标成 `active`。
- `local` 规则出现在 `validate-spec` 里，Go 与 JavaScript 夹具全部通过，`matches` 按 RE2。`server` 规则能读取声明过的关联。`PATCH` 未提交的字段仍以库中的值参加规则。
- 一次 `POST` 能新建订单、挂上已有客户、并新建订单行；中途任意规则失败时，三处都不留新行。`:query` 按主实体分页，跨实体筛选走子查询，列表 `expand` 批量补多对一，列表正文不含 `text` / `json` / `file`。提交成功则同事务写入 `dm_record_change` 并分配连续 `visible_seq`。并发提交时，后提交的事务拿不到更小的序号。
- `purge` 之外的结构操作，目录与 `information_schema` 的类型、可空、精度、索引类型一致。
- 两个并发草稿保存不会产生第二份 `draft`。把可空列改成必填时，仍有 `api` 停在更旧修订上则返回 409。

应用代码：

- 不重新编译平台，能够保存草稿、检查、发布一份含领域包和接口包的修订，并立刻用新路由访问到新函数。
- 发布失败时，原已发布修订继续服务。
- 领域函数里的 `Create` / `Update` 与直接调用 `/api/v1/data` 一样触发 CEL；规则失败时 `Tx` 整单回滚。
- 源码 import `os` 或写出 `go` 语句时，`:check` 失败，运行池不变。
- 两个并发请求不会借到同一个解释器。其中一个请求 panic 后，下一个请求仍能完成，池会补回实例。
- 平台启动夹具包含：双包互调、`Tx` 回滚、只读 `GET` 写操作被拒绝、路由不覆盖 `/api/v1/data`、字面路径优先于同位置的路径参数。
