# 多实例归属

职责：规定多台进程同时跑时，**解释器池谁切换、变更谁消费、DDL 谁执行**。协调只使用已有的 MySQL，第一期不引入 Redis、MQ、独立配置中心。

不负责：解释器沙箱与函数签名（见 [解释器运行时](06-解释器运行时.md)）；变更行格式（见 [变更历史](07-变更历史.md)）；DDL 语句本身（见 [结构同步](02-结构同步.md)）。

依赖：`dm_revision` 的已发布行是扩展代码的权威；`dm_change_consumer.last_seq` 是每个应用消费进度的权威。本模块只增加「谁允许跑」和「各进程装了哪一版」这两层。

## 1. 原则

- **权威在库里，不在某台机器的内存里。** 发布成功只保证 `dm_revision` 已切换。某台进程的 Yaegi 池只是这份权威的本地缓存。
- **写路径（`/api/v1/data`）无进程亲和。** 任意 API 副本都可以写。变更行进同一张表，不绑机器。
- **消费有亲和：每个消费者名字同一时刻只允许一个 leader。** 进度用每个应用的 `last_seq`，资格用租约，两张表分开。
- **结构执行有锁无亲和。** 任意 API 副本都可以抢 `dm_schema_{entityId}` 命名锁并执行 DDL。同一实体仍串行。

单机开发用角色 `all`，把 API 与 worker 放进一个进程。生产禁止 `all`。

## 2. 进程角色

同一份二进制，启动参数决定角色。进程启动时生成 `instance_id`（UUID），写入日志，不进业务表的常规查询。

| 角色 | 进程 | HTTP | 解释器池 | 轮询已发布修订 | 结构执行器 | 变更消费 |
|---|---|---|---|---|---|---|
| `api` | 面向用户的副本 | `/api/v1/model`、`/data`、`/ext`、`/ext-src` | 有 | 有，并写心跳 | 有（命名锁，与 DDL 同一条连接） | 无 |
| `worker` | 后台副本，可只跑 1 个 | 不对外 | 无（第一期消费不调领域函数） | 无 | 无 | 有（先抢租约） |
| `all` | 仅本地 | 全开 | 有 | 有 | 有 | 有（仍抢租约，避免以后误开多进程） |

第一期 worker 只跑变更消费者。以后若消费要调领域函数，再给 worker 加解释器池和同样的修订轮询，不改租约协议。

`POST /api/v1/domain/{appCode}/{funcName}` 第一期不挂到 `api` 的公网路由。只保留进程内调用。以后若开放，必须走服务身份，不能与 `/ext` 一样「已登录即可」。

## 3. 解释器：每台 API 自己跟上库

发布接口的正确性边界是：**库事务提交后，已发布修订已切换**。调用发布的那台机器可以立刻换自己的池，这只是优化，不是协议。其它机器不以这次 HTTP 返回为准。

### 3.1 每台 `api` 进程保持一份本地表

```text
local[appId] = { revisionId, revision, pool }
```

启动时：`SELECT` 每个应用 `phase = published` 的行，建池，填入 `local`。某个应用装载失败：该应用 `/ext` 返回 503，其它应用与 `/data`、`/model` 不受影响。

### 3.2 轮询

每 1 秒（可配 200ms–5s）：

```text
SELECT app_id, id, revision
FROM dm_revision
WHERE phase = 'published'
```

对每个 `app_id`：

| 库中的已发布 | 本地 | 动作 |
|---|---|---|
| 没有该应用 | 有池 | 释放池，该应用 `/ext` 改 404（应用被拆掉，第一期少见） |
| `id` 与本地相同 | 有池 | 不动 |
| `id` 与本地不同 | 任意 | 按该行源码**后台**建新池 |

建池成功：原子指针换上新池，旧池按 [解释器运行时](06-解释器运行时.md) 排空后释放，更新 `local`，并 upsert 第 3.4 节的心跳。  
建池失败：保留当前池，打错误日志，下个轮询周期再试。连续失败超过 3 分钟：该节点该应用 `/ext` 改为 503，并告警。心跳仍写当前装载成功的修订，收紧列的检查因而能看见这台进程还停在旧修订上。

发布方本机在事务提交后走同一套「建池 → 成功才换」；失败时它与其它副本一样继续用内存里的上一份池，直到某次轮询成功。客户端刚收到发布 200，立刻打到尚未换池的副本，仍可能跑旧修订。这是第一期接受的窗口，上限约一个轮询间隔。需要更短窗口就把轮询降到 200ms，不引入消息总线。

不把解释器池写进共享存储，也不在节点间 RPC 传送 Yaegi 状态。

### 3.3 不靠通知通道

进程内「发布成功」唤醒只加速**本进程**的下一次比对，可有可无。其它进程只认轮询结果。

### 3.4 实例心跳

```sql
CREATE TABLE dm_instance_heartbeat (
  instance_id  CHAR(36)        NOT NULL COMMENT 'api 进程启动时生成的 UUID',
  app_id       BIGINT UNSIGNED NOT NULL COMMENT '应用',
  revision_id  BIGINT UNSIGNED NOT NULL COMMENT '本进程当前装载的 dm_revision.id',
  revision     INT UNSIGNED    NOT NULL COMMENT '本进程当前装载的修订号',
  seen_at      DATETIME(3)     NOT NULL COMMENT '最近一次上报，UTC。15 秒内视为新鲜',
  PRIMARY KEY (instance_id, app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT 'api 进程已装载的源码修订';
```

每次轮询比对之后，本进程对每个仍装着池的应用执行：

```sql
INSERT INTO dm_instance_heartbeat (instance_id, app_id, revision_id, revision, seen_at)
VALUES (:instance, :app, :revision_id, :revision, UTC_TIMESTAMP(3))
ON DUPLICATE KEY UPDATE
  revision_id = VALUES(revision_id),
  revision    = VALUES(revision),
  seen_at     = UTC_TIMESTAMP(3);
```

本地池没有换时也刷新 `seen_at`。建池失败时写的是仍在服务的旧修订。应用已经没有 `published` 行时删掉本实例这一行。

`seen_at` 在 15 秒内的行才算新鲜。进程正常退出时删掉自己的行。过期行由任一 `api` 在轮询时删掉。

把可空列改为 `NOT NULL` 时，结构模块要求每个新鲜心跳的 `revision` 都大于等于请求里的 `minRevision`。没有新鲜心跳则拒绝，避免在全部进程都没上报时收紧。见 [结构同步](02-结构同步.md)。

心跳只证明各 `api` 进程的解释器装了哪一版。它不证明浏览器或外部客户端已经会给新字段传值。

## 4. 消费：租约选主

`dm_change_consumer` 只存进度，不存谁在跑。谁在跑放进租约表。

```sql
CREATE TABLE dm_worker_lease (
  name        VARCHAR(40)     NOT NULL COMMENT '消费者名字，与 dm_change_consumer.name 相同',
  owner       CHAR(36)        NOT NULL COMMENT '当前 leader 的 instance_id',
  lease_until DATETIME(3)     NOT NULL COMMENT '租约到期时间，UTC。比较时用 MySQL 的 UTC_TIMESTAMP(3)',
  updated_at  DATETIME(3)     NOT NULL COMMENT '最近一次抢主或续约的时间，UTC',
  PRIMARY KEY (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '变更消费租约。进度在 dm_change_consumer，不在本表';
```

`name` 与消费者名字相同，例如 `log`、`wf_trigger`。没有行时，worker 插入 `owner = 自己的 instance_id`，`lease_until = 现在 + 15 秒`。

### 4.1 抢主与续约

每个 `worker` 对它负责的每个 `name`，每 5 秒尝试：

```text
UPDATE dm_worker_lease
SET owner = :me, lease_until = :now + INTERVAL 15 SECOND, updated_at = :now
WHERE name = :name
  AND (owner = :me OR lease_until < :now)
```

影响行数为 1：本进程是该名字的 leader，允许拉变更。  
影响行数为 0：本进程是 follower，**禁止** `SELECT dm_record_change` 做消费，下一轮再试。

时钟用 MySQL 的 `UTC_TIMESTAMP(3)`，不用各机器本地时钟比较 `lease_until`。应用传入的 `:now` 也取自一次 `SELECT UTC_TIMESTAMP(3)`，避免节点 NTP 漂移把租约判死。

leader 进入消费循环（见 [变更历史第 5 节](07-变更历史.md)）。续约是独立计时器，每 5 秒一次，批处理进行中也跑。单批超时是 30 秒，长于 15 秒租约；若等批处理结束再续约，第二个 worker 会在中途拿到租约。

续约影响行数为 0：取消本批的上下文，停止读取下一批，并且**不许**再 CAS `last_seq`。本批做到一半的副作用靠消费者幂等，由下一个 leader 重放。worker 同时按 [变更历史](07-变更历史.md) 清理超过 90 天且已被全部已登记消费者越过的变更行。

进程退出前尽力：

```text
UPDATE dm_worker_lease
SET lease_until = :now
WHERE name = :name AND owner = :me
```

让其它 worker 不必等满 15 秒。杀 -9 时做不到，最多停消费 15 秒，可接受。

### 4.2 为什么 CAS `last_seq` 不够

`last_seq` 的 CAS 发生在**处理完一批之后**。若三台进程都先 `SELECT` 同一批、都处理、再 CAS，只有一个推进游标，但业务副作用已经发生三次。租约把「允许 SELECT 去处理」限制成一台，CAS 只作为租约失效时的第二道闸。两道都要。续约失败的那一台连 CAS 也不做。

`api` 角色进程不启动消费循环，从根上避免「副本数等于消费者数」。本地 `all` 仍走租约，这样开两个 `all` 也不会双消费。

### 4.3 第一期部署

生产：`api` 水平扩展；`worker` 部署 **1 个**即可。租约是为了第二个 worker 起来做故障转移，不是为了并行加速。同一 `name` 不要分片。

## 5. 结构执行器

`api` 进程执行 DDL，用命名锁 `dm_schema_{entityId}`。`GET_LOCK`、DDL、`RELEASE_LOCK` 在从池中取出的同一条连接上完成。多副本同时点重试，只有拿到锁的那个跑，其它等或拿到锁后发现任务已 `applied` 则退出。不另做选主。哪些请求等待 DDL、哪些直接 202，见 [结构同步](02-结构同步.md)。

## 6. 本模块完成标准

- 三台 `api` 同时跑：在其中一台发布后，在轮询间隔内三台 `/ext` 都切到同一 `revision`；发布事务回滚则三台都不切。
- 一台 `api` 装载新修订失败：该台暂时留旧池或 503，其它台不受影响；修复源码或内存后该台自行跟上，不需要整集群重启。
- 两台 `worker` 同时跑同一 `name`：任意时刻只有一台 `SELECT` 消费；杀掉 leader 后，另一台在 15 秒内接上且 `last_seq` 不回退。处理超过 15 秒的批次期间，leader 仍在续约；续约失败的进程不会推进游标。
- 一台 `api` 仍停在旧修订时，把某列改成 `NOT NULL` 返回 409，并带上该 `instance_id`。该进程装上 `minRevision` 之后，同一请求可以通过心跳检查。
- 只起 `api`、不起 `worker`：`/data` 写入仍进 `dm_record_change`，游标不前进；补上 worker 后能从断点追上。
- 角色 `all` 单进程通过上述发布与消费的功能测试；两个 `all` 同时跑时消费仍只有一个 leader。
