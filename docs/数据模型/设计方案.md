# 数据模型设计方案

产品名称用「数据模型」。代码里一类业务数据叫实体 `entity`，实体上的一项属性叫字段 `field`，实体之间可导航的连接叫关联 `link`。描述这些结构的数据在文档里称目录。

本方案要落地三件事：

1. 用 API 增加、修改、删除实体和结构，并让 MySQL 物理表跟上目录。
2. 校验规则用 CEL 文本保存。服务端用 cel-go 执行，前端执行同一段文本。
3. 一次数据 API 在同一个数据库事务里写入当前表和关联表。

实现栈：Go、GoFrame、MySQL 8、cel-go。组织是单组织、多应用。实体归属某个应用。

## 1. 三份数据

| 份 | 存在哪 | 谁写入 | 谁读取 |
|---|---|---|---|
| 目录 | `dm_*` 表 | 结构 API | 结构 API、数据 API、管理后台 |
| 物理表 | `information_schema` 里的业务表 | 结构执行器跑 DDL | 数据 API |
| 业务记录 | 各实体物理表、多对多中间表 | 数据 API | 数据 API |

目录是目标结构。物理表是已经执行成功的结构。两者允许短暂不一致：字段处于 `pending` 或 `failed` 时，数据 API 看不见它。

页面、审批、工作流、权限不写入目录。它们只引用已经生效的 `entityCode`、`fieldCode`、`linkCode`。

## 2. 原则

- 编码创建后不改。显示名可以改。物理表名、物理列名在创建时定死，之后不随显示名变化。
- 结构 API 先提交目录和一条结构任务，再在事务外执行 DDL。MySQL 的 `ALTER TABLE` 会隐式提交当前事务，不能把目录更新和 DDL 放进同一个事务。
- 数据写入只使用状态为 `active` 的字段和关联，并且全部 DML 放在一个 InnoDB 事务里。
- 关联是独立对象，不把「一对多」做成当前表上的一个列。当前表上只为「多对一 / 一对一」放外键列。
- CEL 只做跨字段、跨记录的业务规则。必填、类型、长度、唯一由目录和数据库约束负责。
- 能在浏览器里跑的规则，和必须读库的规则分开存。保存规则时就拒绝前端跑不了的写法。

## 3. 标识与物理名

应用编码、实体编码、字段编码、关联编码、选项编码、规则编码使用同一套规则：

```text
^[a-z][a-z0-9_]{0,40}$
```

禁止使用第 7 节列出的系统列名，以及 MySQL 保留字。

物理名只在创建时生成一次，记在目录里：

| 对象 | 物理名 |
|---|---|
| 实体表 | `{appCode}__{entityCode}` |
| 字段列 | 字段编码 |
| 普通索引 | `ix_{entityId}_{indexId}` |
| 外键 | `fk_{linkId}` |
| 多对多中间表 | `j_{linkId}` |

表名、列名、索引名、外键名的长度必须 `<= 64`。超长则创建接口直接失败，不截断、不哈希。`appCode` 与 `entityCode` 因此要在创建时一起算长度。

业务表统一 `InnoDB`、`utf8mb4`、`utf8mb4_0900_ai_ci`。时间列用 `DATETIME(3)`，按 UTC 写入。

## 4. 逻辑类型

第一期字段只有下表这些种类。公式、自动编号、树、视图不在这一期。

| kind | scalar_type | MySQL | API JSON | CEL 里的类型 |
|---|---|---|---|---|
| scalar | string | `VARCHAR(n)`，n 默认 255，最大 1000 | 字符串 | string |
| scalar | text | `TEXT` | 字符串 | string |
| scalar | int | `INT` | 数字 | int |
| scalar | bigint | `BIGINT` | 数字 | int |
| scalar | decimal | `DECIMAL(p,s)`，默认 `(18,4)` | 十进制字符串 | string |
| scalar | bool | `TINYINT(1)` | `true` / `false` | bool |
| scalar | date | `DATE` | `YYYY-MM-DD` | string |
| scalar | datetime | `DATETIME(3)` | UTC RFC3339，毫秒 | string |
| scalar | json | `JSON` | 对象或数组 | 第一期不进入 CEL |
| option | — | `VARCHAR(40)`，存选项编码 | 字符串 | string |
| file | — | `JSON`，文件 id 数组 | 数字数组 | 第一期不进入 CEL |
| ref | — | `BIGINT UNSIGNED`，外键 | 不放在 `values` 里，走关联写入 | 不进入 CEL |

`decimal` 用字符串进出 API，避免二进制浮点。`p` 取值 1–38，`s` 取值 0–p，且 `p <= 38`。`string` 的 `n` 取值 1–1000。

选项集在应用内共享。字段只引用选项集，不在字段上复制一份选项。

`ref` 列只出现在「多」的一侧，用来承载多对一或一对一。一对多没有自己的列，它是对方外键的反向导航名。多对多没有业务列，使用中间表。

成员、部门不单设字段种类。需要时建成指向组织模块实体的 `ref`。组织模块尚未建模时，先不在业务表里放裸的成员 id 列。

## 5. 每张业务表固定带上的列

创建实体时由执行器建表，目录里同时插入 `origin = system` 的字段行。这些字段不能通过字段 API 修改或删除。

```sql
id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
created_at     DATETIME(3)     NOT NULL
created_by     BIGINT UNSIGNED NOT NULL
updated_at     DATETIME(3)     NOT NULL
updated_by     BIGINT UNSIGNED NOT NULL
deleted_at     DATETIME(3)     NULL
deleted_token  BIGINT UNSIGNED NOT NULL DEFAULT 0
PRIMARY KEY (id)
```

`soft_delete = 1` 时，删除把 `deleted_at` 写成当前 UTC 时间，并把 `deleted_token` 写成该行 `id`。未删除行的 `deleted_token` 保持 0。列表默认加 `deleted_token = 0`。

唯一约束一律建成 `(业务列…, deleted_token)`。这样软删除后，同一业务键可以再次使用。实体若关闭软删除，则不建 `deleted_at` 与 `deleted_token`，唯一索引只含业务列，删除改为物理 `DELETE`。第一期建议所有业务实体都开启软删除，创建后再改这个开关会牵涉唯一索引重建，接口不提供该开关的修改。

`created_by` / `updated_by` 来自当前登录用户，请求体里的同名键忽略。

## 6. 目录表

### 6.1 dm_entity

```sql
CREATE TABLE dm_entity (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  app_id        BIGINT UNSIGNED NOT NULL,
  app_code      VARCHAR(40)     NOT NULL,
  code          VARCHAR(40)     NOT NULL,
  title         VARCHAR(80)     NOT NULL,
  table_name    VARCHAR(64)     NOT NULL,
  title_field   VARCHAR(40)     NULL,
  soft_delete   TINYINT(1)      NOT NULL DEFAULT 1,
  revision      INT UNSIGNED    NOT NULL DEFAULT 0,
  status        VARCHAR(16)     NOT NULL,
  created_at    DATETIME(3)     NOT NULL,
  updated_at    DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_entity_app_code (app_id, code),
  UNIQUE KEY uk_dm_entity_table (table_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`status`：`active`、`archived`。`revision` 在每次结构任务成功后加 1。`app_code` 是生成 `table_name` 时的副本，应用以后改编码也不改表名。`title_field` 指向一个 `active` 的 `string` 或 `option` 字段，供关联展示使用；可以后补。

### 6.2 dm_field

```sql
CREATE TABLE dm_field (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  entity_id     BIGINT UNSIGNED NOT NULL,
  code          VARCHAR(40)     NOT NULL,
  title         VARCHAR(80)     NOT NULL,
  kind          VARCHAR(16)     NOT NULL,
  scalar_type   VARCHAR(16)     NULL,
  char_length   INT             NULL,
  num_precision INT             NULL,
  num_scale     INT             NULL,
  required      TINYINT(1)      NOT NULL DEFAULT 0,
  option_set_id BIGINT UNSIGNED NULL,
  origin        VARCHAR(16)     NOT NULL,
  status        VARCHAR(16)     NOT NULL,
  sort_no       INT             NOT NULL DEFAULT 0,
  created_at    DATETIME(3)     NOT NULL,
  updated_at    DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_field_entity_code (entity_id, code),
  KEY idx_dm_field_entity_status (entity_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`kind`：`scalar`、`option`、`file`、`ref`。`origin`：`system`、`custom`。`status`：`pending`、`active`、`failed`、`retired`。

单列唯一不放在本表，统一走 `dm_index`，便于和软删除令牌拼在一起。

`ref` 字段的目标实体记录在 `dm_link`，不在本表重复一份。

### 6.3 dm_link

一条 `dm_link` 表示一种关联，同时给出两侧的导航名。

```sql
CREATE TABLE dm_link (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  app_id             BIGINT UNSIGNED NOT NULL,
  kind               VARCHAR(16)     NOT NULL,
  owner_entity_id    BIGINT UNSIGNED NOT NULL,
  owner_field_id     BIGINT UNSIGNED NULL,
  owner_nav_code     VARCHAR(40)     NOT NULL,
  target_entity_id   BIGINT UNSIGNED NOT NULL,
  target_nav_code    VARCHAR(40)     NOT NULL,
  junction_table     VARCHAR(64)     NULL,
  on_delete          VARCHAR(16)     NOT NULL,
  required           TINYINT(1)      NOT NULL DEFAULT 0,
  status             VARCHAR(16)     NOT NULL,
  created_at         DATETIME(3)     NOT NULL,
  updated_at         DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_link_owner_nav (owner_entity_id, owner_nav_code),
  UNIQUE KEY uk_dm_link_target_nav (target_entity_id, target_nav_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

| kind | 外键放在哪 | owner 侧导航 | target 侧导航 | 数据 API 含义 |
|---|---|---|---|---|
| many_to_one | owner 表的 `owner_field_id` | 多对一，例如订单上的 `customer` | 一对多，例如客户上的 `orders` | `set` 改外键；在 target 侧 `create` 会插入 owner 行 |
| one_to_one | owner 表的 `owner_field_id`，并加唯一索引 | 一对一 | 反向一对一 | 同上，外键列在未删除行中唯一 |
| many_to_many | `junction_table` | 导航名 | 反向导航名 | `link` / `unlink` 写中间表 |

`on_delete`：`restrict` 或 `set_null`。`set_null` 要求外键列可空，且 `required = 0`。第一期不做数据库级 `ON DELETE CASCADE`，避免管理端一次删除扫掉大片业务数据。应用层若要级联删除，以后单独立项。

两侧导航编码在各自实体上唯一，且不能与该实体的字段编码相同。数据 API 因此可以用一个命名空间解析 `values` 以外的键。

自关联允许：`owner_entity_id = target_entity_id`，但两个导航编码必须不同。

### 6.4 dm_index 与 dm_index_column

```sql
CREATE TABLE dm_index (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  entity_id   BIGINT UNSIGNED NOT NULL,
  code        VARCHAR(40)     NOT NULL,
  unique_key  TINYINT(1)      NOT NULL,
  index_name  VARCHAR(64)     NOT NULL,
  status      VARCHAR(16)     NOT NULL,
  created_at  DATETIME(3)     NOT NULL,
  updated_at  DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_index_entity_code (entity_id, code),
  UNIQUE KEY uk_dm_index_name (index_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE dm_index_column (
  index_id  BIGINT UNSIGNED NOT NULL,
  field_id  BIGINT UNSIGNED NOT NULL,
  seq       INT             NOT NULL,
  PRIMARY KEY (index_id, seq),
  UNIQUE KEY uk_dm_index_column (index_id, field_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

唯一索引在软删除实体上的物理列序是：声明的字段顺序，最后加 `deleted_token`。非唯一索引不加 `deleted_token`。

索引列只能是 `active` 的 `string`、`int`、`bigint`、`decimal`、`bool`、`date`、`datetime`、`option`、`ref`。`text`、`json`、`file` 不参与索引。列数 1–5。

  sort_no     INT             NOT NULL DEFAULT 0,

停用选项后，新写入不能再使用该编码，已有行仍可读出。删除选项编码会造成历史值无法解释，接口不提供物理删除，只提供停用。

### 6.6 dm_rule

```sql
CREATE TABLE dm_rule (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  entity_id   BIGINT UNSIGNED NOT NULL,
  code        VARCHAR(40)     NOT NULL,
  title       VARCHAR(80)     NOT NULL,
  scope       VARCHAR(16)     NOT NULL,
  expr        TEXT            NOT NULL,
  message     VARCHAR(200)    NOT NULL,
  reads_json  JSON            NULL,
  enabled     TINYINT(1)      NOT NULL DEFAULT 1,
  sort_no     INT             NOT NULL DEFAULT 0,
  created_at  DATETIME(3)     NOT NULL,
  updated_at  DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_rule (entity_id, code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`scope`：`local` 或 `server`。`reads_json` 仅 `server` 使用，内容是导航编码数组。规则的增删改只写目录，不产生 DDL，保存成功即生效。`expr` 必须编译通过，且求值结果类型为 `bool`。

### 6.7 dm_schema_task

```sql
CREATE TABLE dm_schema_task (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  entity_id    BIGINT UNSIGNED NOT NULL,
  action       VARCHAR(32)     NOT NULL,
  target_kind  VARCHAR(16)     NOT NULL,
  target_id    BIGINT UNSIGNED NOT NULL,
  forward_ddl  TEXT            NOT NULL,
  reverse_ddl  TEXT            NULL,
  status       VARCHAR(16)     NOT NULL,
  error_text   TEXT            NULL,
  created_at   DATETIME(3)     NOT NULL,
  started_at   DATETIME(3)     NULL,
  applied_at   DATETIME(3)     NULL,
  PRIMARY KEY (id),
  KEY idx_dm_schema_task_entity (entity_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`action`：`create_table`、`add_column`、`modify_column`、`drop_column`、`add_index`、`drop_index`、`add_fk`、`drop_fk`、`create_junction`、`drop_junction`。

`status`：`pending`、`running`、`applied`、`failed`。

同一实体只允许一条 `pending` 或 `running` 任务。结构 API 用 `SELECT … FOR UPDATE` 锁住 `dm_entity` 行来保证这一点。

## 7. 系统字段

下列编码保留，不能作为自定义字段或导航编码：

```text
id, created_at, created_by, updated_at, updated_by, deleted_at, deleted_token
```

对应的 `dm_field` 行在建表任务成功后插入，`origin = system`，`status = active`。数据 API 的 `values` 不接受这些键。读记录时，`id` 与审计列放在记录外层，不放进 `values`。

## 8. 结构 API

前缀 `/api/v1/model`。调用方是管理后台和搭建用的 Skill。请求都带应用标识，实体编码在应用内查找。

```text
POST   /apps/{appCode}/entities
PATCH  /apps/{appCode}/entities/{entityCode}
POST   /apps/{appCode}/entities/{entityCode}:archive

POST   /apps/{appCode}/option-sets
POST   /apps/{appCode}/option-sets/{setCode}/items
PATCH  /apps/{appCode}/option-sets/{setCode}/items/{itemCode}

POST   /apps/{appCode}/entities/{entityCode}/fields
PATCH  /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}
POST   /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}:retire
POST   /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}:purge

POST   /apps/{appCode}/entities/{entityCode}/links
POST   /apps/{appCode}/entities/{entityCode}/links/{navCode}:retire

POST   /apps/{appCode}/entities/{entityCode}/indexes
DELETE /apps/{appCode}/entities/{entityCode}/indexes/{indexCode}

POST   /apps/{appCode}/entities/{entityCode}/rules
PATCH  /apps/{appCode}/entities/{entityCode}/rules/{ruleCode}
DELETE /apps/{appCode}/entities/{entityCode}/rules/{ruleCode}

GET    /apps/{appCode}/entities/{entityCode}
GET    /apps/{appCode}/entities/{entityCode}/validate-spec
POST   /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}:retry
```

### 8.1 一次结构变更的顺序

以新增字段为例：

1. 校验编码、类型、长度、选项集是否属于同一应用。
2. 开启短事务，锁 `dm_entity`。若该实体已有 `pending` / `running` 任务，返回 409。
3. 插入 `dm_field`，`status = pending`。插入 `dm_schema_task`，写好 `forward_ddl` 与 `reverse_ddl`。提交。
4. 事务结束后执行该任务。执行器对实体使用 MySQL 命名锁 `dm_schema_{entityId}`，把任务改为 `running`，然后单独执行 DDL。
5. DDL 成功：任务改为 `applied`，字段改为 `active`，`dm_entity.revision` 加 1。
6. DDL 失败：任务改为 `failed`，字段改为 `failed`，`error_text` 记下 MySQL 错误。接口返回 500，响应里带 `taskId`。

数据 API 只认 `active`。`pending`、`failed`、`retired` 都不会出现在写入和校验说明里。

`retry` 只接受 `failed` 任务。重试前执行器查看 `information_schema`：列已经存在则把目录改成 `active`，不再执行 DDL；列不存在则原样重跑 `forward_ddl`。

GoFrame 侧，目录与业务 DML 走 `gdb` 事务；DDL 用单独的 `Exec`，不包在 `Transaction` 回调里。

### 8.2 允许的结构改动

创建实体时一次建出系统列，并插入系统字段的目录行。此时还没有自定义字段。

| 操作 | 目录 | DDL |
|---|---|---|
| 改显示名、排序、标题字段 | 直接更新 | 无 |
| 加字段 | `pending` → `active` | `ADD COLUMN`，新列先可空 |
| 放宽 `VARCHAR` 长度 | 更新 `char_length` | `MODIFY COLUMN` |
| 增大 `DECIMAL` 的精度且标度不变或变大 | 更新精度 | `MODIFY COLUMN` |
| 把可空改为必填 | 先查该列不存在 `NULL`，通过后更新 | `MODIFY COLUMN … NOT NULL` |
| 把必填改为可空 | 更新 | `MODIFY COLUMN … NULL` |
| 停用字段 | `retired` | 无 |
| 清除已停用字段 | 删除目录行 | `DROP COLUMN` |
| 加索引、删索引 | 对应任务 | `ADD INDEX` / `DROP INDEX` |
| 加关联 | 字段任务 + 外键或中间表任务，按顺序两条任务排队 | `ADD COLUMN` 后 `ADD CONSTRAINT`，或 `CREATE TABLE` 中间表 |

下列改动接口直接拒绝：

- 修改任意编码、物理表名、物理列名
- 修改 `kind` 或 `scalar_type`
- 缩短字符串、减小数值精度、减小标度
- 更换关联的目标实体
- 删除仍被关联引用的字段
- 归档仍被其他 `active` 关联指向的实体

停用后的字段仍留在表上，历史行还在。`purge` 要求当前状态是 `retired`，并且请求带 `confirm=true`。`purge` 的 `reverse_ddl` 为空，数据不可自动找回。

归档实体只改 `status = archived`，不删表。数据 API 拒绝读写。归档前要求没有指向它的 `active` 关联。

### 8.3 新增关联时目录里有什么

新增多对一 `order.customer → customer.orders`：

1. 在订单上插入 `kind = ref` 的字段，编码等于 `owner_nav_code`（`customer`），任务是 `add_column`。
2. 插入 `dm_link`，`status = pending`。
3. 列任务成功后，再插入 `add_fk` 任务。外键引用 `customer.id`。
4. 两条都成功后，字段与关联改为 `active`。

一对一相同，并额外插入一条唯一索引任务，列是该外键加 `deleted_token`。

新增多对多只插入 `dm_link` 和一条 `create_junction` 任务。中间表：

```sql
CREATE TABLE j_12 (
  owner_id   BIGINT UNSIGNED NOT NULL,
  target_id  BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3)     NOT NULL,
  PRIMARY KEY (owner_id, target_id),
  KEY idx_j_12_target (target_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

中间表不软删除。`unlink` 是物理删除中间行，不删除两端业务行。

## 9. CEL 校验

### 9.1 规则看什么

保存时把表达式放进受控环境编译。环境版本号为 `cel-profile/v1`。

`local` 规则的变量只有：

```text
record.<fieldCode>
old.<fieldCode>
```

`record` 是类型转换和标准化之后、写入之前的当前行。`old` 在创建时各字段为 `null`，在更新时是库里的当前行。两边都只有第 4 节标成可进入 CEL 的字段。`json`、`file`、`ref` 不在环境里。

`server` 规则在上述变量之外增加：

```text
link.<navCode>
```

`reads_json` 里声明的导航才会被放进环境。多的一侧是列表，一的一侧是单个 map 或 `null`。map 的键是目标实体里允许进入 CEL 的字段，外加 `id`。未声明的导航不能出现在表达式里。

第一期函数白名单：

- 比较与逻辑：`== != < <= > >= && || !`
- 字符串与集合：`contains`、`startsWith`、`endsWith`、`matches`、`size`、`in`
- 十进制：`decCmp(a, b)` 返回 int，`decAdd`、`decSub`、`decMul` 的参数和返回值都是十进制字符串

不提供 `now`、自定义 IO、反射数据库。时间比较使用标准化后的 UTC 字符串。CEL 本身没有用户可写的循环；`.exists` 一类宏只允许作用在本次请求已经装入的 `link` 列表上。

`local` 规则的表达式若引用 `link`、`old` 以外的未知标识，或调用白名单外的函数，保存接口返回 400。`server` 规则不允许下发给前端。

### 9.2 前后端怎么跑同一段 CEL

服务端使用 cel-go：按 `cel-profile/v1` 建环境，编译结果按表达式文本的哈希缓存，求值结果必须是 `bool`。`false` 表示校验失败，把规则的 `code` 和 `message` 返回给调用方。

前端不嵌入 cel-go。前端使用一份对齐 CEL 规范的 JavaScript 实现，只开启同一份函数白名单，并实现同样的 `decCmp`、`decAdd`、`decSub`、`decMul`。

两边在求值前做同一种标准化：

- 字符串去掉首尾空白；空字符串视为 `null`
- `decimal` 去掉多余的 0 和指数形式，保留标度内的十进制字符串
- `datetime` 转成 UTC、毫秒三位的 RFC3339
- `date` 保持 `YYYY-MM-DD`
- `bool` 只接受 JSON 布尔

`GET …/validate-spec` 返回前端执行所需要的全部信息：`profile`、字段的 CEL 类型、标准化规则名、全部 `enabled` 且 `scope = local` 的表达式与文案。不返回 `server` 规则。

仓库里放一组 JSON 夹具：表达式、标准化前输入、期望布尔值。Go 与 JavaScript 各跑一遍。白名单或标准化有改动时，先改夹具再改两端实现。

服务端在写入路径上仍会执行全部 `local` 规则。前端校验只减少往返，不作为安全边界。

### 9.3 一条写入里的校验顺序

对图中的每一行：

1. 拒绝未知字段、未知导航、类型不匹配的 JSON。
2. 按第 9.2 节标准化。
3. 检查必填、字符串长度、小数精度、选项编码是否启用、外键目标是否存在。
4. 执行该实体的 `local` 规则。
5. 装入 `reads_json` 声明的关联：请求里已经带上的用请求数据，没带上的在当前事务里 `SELECT`。
6. 执行 `server` 规则。
7. `INSERT` 或 `UPDATE`。

任一步失败则整个数据事务回滚。响应使用 422，正文列出 `entityCode`、行临时键、`ruleCode` 或约束名、`message`。

## 10. 数据 API：当前表和关联表

前缀 `/api/v1/data`。

```text
POST   /{entityCode}
PATCH  /{entityCode}/{id}
GET    /{entityCode}/{id}?expand=customer,lines
```

请求体：

```json
{
  "values": {
    "title": "PO-1",
    "amount": "12.50"
  },
  "links": {
    "customer": { "op": "set", "id": 9 },
    "lines": {
      "op": "append",
      "items": [
        {
          "values": { "sku": "A", "qty": 2 },
          "links": { "product": { "op": "set", "id": 3 } }
        }
      ]
    }
  }
}
```

`values` 只含当前实体的标量、选项、文件字段。关联一律写在 `links` 里。

### 10.1 操作与关联种类

| op | 适用 | 行为 |
|---|---|---|
| `set` | 多对一、一对一 | 把外键改成已存在的 `id`；`id` 为 `null` 时清空，列不可空则拒绝 |
| `create` | 多对一、一对一、一对多 | 插入关联行。一对多时把新行的外键设为当前行 |
| `update` | 一对多、多对一已存在的目标 | 按 `id` 更新该行的 `values` 与更深层 `links` |
| `remove` | 一对多 | 按该实体的软删除规则删除子行 |
| `link` | 多对多 | 插入中间表，两端行必须已存在 |
| `unlink` | 多对多 | 删除中间表对应行 |

`create` 的元素可以继续带 `links`。从一个根行算起，嵌套深度最多 3。一次请求最多 100 个写节点。图里不允许出现环。

第一期不提供「用一份列表替换全部子行」。调用方明确使用 `append`、`update`、`remove`。

`set` 与 `link` 不创建目标行，避免一次保存意外插入主数据。要新建目标，使用 `create`。

### 10.2 事务内的写入顺序

1. 解析整张图，核对导航种类与 `op` 是否匹配。
2. `BEGIN`。
3. 先写根行。根行是新建时，子行要等根行 `id` 出来后再写外键。
4. 多对一的 `create`：先插入目标行，再把目标 `id` 回填到当前行外键并更新。若当前行也是本次新建，则在 `INSERT` 时直接写入该外键，避免多一次更新。
5. 一对多的 `create`：插入子行，外键列为根行 `id`。
6. 多对多在两端 `id` 都确定后写中间表。
7. 每插入或更新一行之前，跑完第 9.3 节的校验。`server` 规则能看见本事务里已经写入的行。
8. `COMMIT`。失败则 `ROLLBACK`，不留下半张订单。

更新使用 `UPDATE … WHERE id = ? AND deleted_token = 0`。影响行数为 0 则回滚并返回 404。

物理表名只从目录读取，不拼接调用方传来的任意字符串。

### 10.3 读写使用同一形状

`GET` 的 `expand` 列出导航编码。未展开的关联不出现在响应里。写入成功的响应返回根行 `id`，以及本次请求写过的那棵图，形状与 `GET` 一致：

```json
{
  "id": 41,
  "created_at": "2026-11-01T14:00:00.000Z",
  "updated_at": "2026-11-01T14:00:00.000Z",
  "values": { "title": "PO-1", "amount": "12.50" },
  "links": {
    "customer": { "id": 9, "title": "Acme" },
    "lines": [
      { "id": 7, "values": { "sku": "A", "qty": 2 } }
    ]
  }
}
```

关联上的 `title` 来自目标实体的 `title_field`。目标没有标题字段时只返回 `id`。

列表、筛选、分页不在本方案展开。它们以后走同一套目录和同一套 `active` 字段，不另建一套字段定义。

## 11. 并发、失败与核对

- 同一实体的结构任务串行。不同实体可以并行。外键任务若依赖另一个实体的表，那个实体必须已经 `active`。
- 执行器崩溃留下 `running` 时，重启后先查 `information_schema` 再决定重跑或确认成功。判断依据是目录里记下的物理名是否已经存在，而不是任务状态本身。
- 提供管理用核对：比较某实体 `active` 字段与 `information_schema.COLUMNS`，比较 `active` 索引与 `STATISTICS`，比较外键与 `KEY_COLUMN_USAGE`。只报告差异，不自动删列。
- 数据事务与结构任务互不嵌套。结构任务进行中时，该实体的数据 API 仍可写已 `active` 的列；新列要等任务 `applied`。

## 12. 和权限、流程的边界

目录不存角色、数据范围、节点和页面。

数据 API 留两个挂点，第一期可以先放行，接 Cerbos 时不改表结构：

- 写之前：按实体、字段、关联判断当前用户能否写这些键。不能写的键返回 403，不进入校验。
- 读之前：按数据范围追加 `WHERE`。范围条件由权限模块生成，数据 API 只接收已解析的记录集合。

工作流要写业务表时，调用同一套数据 API，不直接 `INSERT` 物理表。这样 CEL、外键和事务顺序只有一条路径。

## 13. 第一期做完的标准

- 能通过 API 创建应用内实体，增加第 4 节的字段，增加多对一、一对一、一对多导航和多对多，增加唯一索引和普通索引。
- 字段停用、清除、实体归档按第 8.2 节的限制工作。失败任务可以安全重试。
- `local` 规则出现在 `validate-spec` 里，Go 与 JavaScript 夹具全部通过。`server` 规则能读取声明过的关联。
- 一次 `POST` 能新建订单、挂上已有客户、并新建订单行；中途任意规则失败时，三处都不留新行。
- `purge` 之外的结构操作，目录与 `information_schema` 核对无差异。
