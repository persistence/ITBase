# 数据模型设计方案 v1.1

v1.1 在 [设计方案](设计方案.md) 之上增加一层用 Yaegi 解释执行的应用代码。这层只增加行为：新的领域函数、新的 HTTP 接口。实体、字段、关联、CEL、物理表仍由 v1 的结构 API 和数据写入管线负责。

实现栈在 v1 的 Go、GoFrame、MySQL 8、cel-go 之外，增加 Yaegi。Yaegi 的版本写进 `go.mod`，与平台使用的 Go 版本一起固定。升级 Yaegi 时先跑通本文第 10 节的夹具再换版本。

## 1. 两层代码

每个应用有一份已发布的源码，里面两个 Go 包：

| 包 | 路径 | 职责 |
|---|---|---|
| 领域 | `itbase.app/{appCode}/domain` | 业务动作：读目录内的记录、按 v1 的写入图修改当前表和关联表、组织一个事务 |
| 接口 | `itbase.app/{appCode}/api` | 解析 HTTP，调用领域函数，把结果写成响应 |

接口包可以 import 本应用的领域包。领域包不 import 接口包。宿主进程不把 `*gdb.DB`、SQL 字符串、DDL、标准库 `os` / `net` 交给解释器。

领域函数对宿主的入口签名全部相同，方便发布时做类型断言：

```go
func(ctx context.Context, in itb.Input) (itb.Output, error)
```

接口函数签名：

```go
func(ctx context.Context, req itb.Request) (itb.Response, error)
```

包内部可以有自己的结构体和未导出函数。宿主只查找导出的、符合上面签名的函数。

一个应用同时只有一份草稿和一份正在服务的已发布修订。流量只进入已发布修订。

## 2. 宿主交给解释器的包

解释器里的 import 路径是 `itbase.dev/itb`。符号表用 `yaegi extract` 从宿主这个包生成，随平台二进制发布。解释器启动时只 `Use` 这份符号表，以及第 7 节列出的标准库子集。不加载 Yaegi 自带的全量 `stdlib.Symbols`。

```go
type Actor struct {
    UserID uint64
}

type Input struct {
    Actor Actor
    Body  map[string]any
}

type Output struct {
    Body map[string]any
}

type Request struct {
    Actor   Actor
    Params  map[string]string
    Query   map[string]string
    Body    map[string]any
    Header  map[string]string
}

type Response struct {
    Status int            // 0 视为 200
    Body   map[string]any
}

type Record struct {
    ID        uint64
    CreatedAt string
    UpdatedAt string
    Values    map[string]any
    Links     map[string]any
}

type Write struct {
    Values map[string]any
    Links  map[string]Link
}

type Link struct {
    Op    string
    ID    *uint64
    Items []WriteItem
}

type WriteItem struct {
    ID     uint64
    Values map[string]any
    Links  map[string]Link
}
```

`Write` / `Link` 的字段与 v1 第 10 节的 JSON 对应。`Op` 只接受 `set`、`create`、`update`、`remove`、`link`、`unlink`。深度、节点数、环检测仍由宿主写入管线执行。`decimal` 在 `map` 里保持十进制字符串。

`App` 是解释器能碰到的唯一数据端口。它由宿主在每次调用时注入，并且已经绑定当前登录人和当前应用：

```go
func Current(ctx context.Context) (*App, error)

func (a *App) Read(ctx context.Context, entity string, id uint64, expand []string) (Record, error)
func (a *App) Query(ctx context.Context, q Query) ([]Record, error)
func (a *App) Create(ctx context.Context, entity string, w Write) (Record, error)
func (a *App) Update(ctx context.Context, entity string, id uint64, w Write) (Record, error)
func (a *App) Delete(ctx context.Context, entity string, id uint64) error
func (a *App) Tx(ctx context.Context, fn func(tx *App) error) error

func Eq(field string, value any) Filter
func Ne(field string, value any) Filter
func Gt(field string, value any) Filter
func Lt(field string, value any) Filter
func Gte(field string, value any) Filter
func Lte(field string, value any) Filter
func In(field string, values []any) Filter
func IsNull(field string, null bool) Filter
func And(parts ...Filter) Filter
func Or(parts ...Filter) Filter

func NewQuery(entity string) Query // 再链式 Where / Order / Limit
```

`Create`、`Update`、`Delete` 进入 v1 第 9、10、12 节的同一条管线：只认 `active` 字段和关联，做标准化、必填、CEL、权限挂点，成功才落库。解释器里写不出绕过 CEL 的插入。

`Read` 与 `Query` 同样只暴露 `active` 字段。`expand` 的元素是导航编码。`Query` 的条件由上面的构造函数拼出，宿主按目录把字段编码映射成列名，使用参数化 SQL。一次查询只有一个实体，不写 JOIN。要沿关联取数，先查主实体，再按 id `Read`。条件树深度最多 3，叶子最多 20。`Limit` 默认 50，最大 200。排序字段最多一个。

`Tx` 把回调里的读写放进同一个 InnoDB 事务，供「改订单并写订单行」这类动作使用。回调里的 `*App` 复用这个事务。嵌套 `Tx` 返回错误。回调返回错误则回滚。事务外的 `Create` / `Update` / `Delete` 各自独立提交，语义与直接调用数据 API 相同。

`GET` 路由使用的 `*App` 是只读视图：`Create`、`Update`、`Delete`、`Tx` 直接返回错误。

业务错误使用宿主类型，接口层可以原样返回：

```go
func Fail(status int, code, message string) error
```

`status` 取 400、404、409、422。其它错误和解释器 panic 由宿主记成 500，响应不带源码和栈。栈只进服务端日志。

## 3. 源码怎么存

```sql
CREATE TABLE dm_revision (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  app_id       BIGINT UNSIGNED NOT NULL,
  revision     INT UNSIGNED    NOT NULL,
  phase        VARCHAR(16)     NOT NULL,
  created_at   DATETIME(3)     NOT NULL,
  published_at DATETIME(3)     NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_revision (app_id, revision),
  KEY idx_dm_revision_phase (app_id, phase)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE dm_file (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  revision_id BIGINT UNSIGNED NOT NULL,
  layer       VARCHAR(16)     NOT NULL,
  filename    VARCHAR(80)     NOT NULL,
  source      MEDIUMTEXT      NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_file (revision_id, layer, filename)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE dm_route (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  revision_id   BIGINT UNSIGNED NOT NULL,
  method        VARCHAR(8)      NOT NULL,
  path_template VARCHAR(160)    NOT NULL,
  handler       VARCHAR(80)     NOT NULL,
  timeout_ms    INT             NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_route (revision_id, method, path_template)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`phase`：`draft`、`published`、`retired`。每个应用最多一行 `draft`、最多一行 `published`。`revision` 从 1 递增。草稿的 `revision` 取「已发布最大号 + 1」，发布成功后该行改为 `published`，原先的 `published` 改为 `retired`。

`layer`：`domain` 或 `api`。`filename` 匹配 `^[a-z][a-z0-9_]{0,40}\.go$`。文件的 `package` 子句必须与 `layer` 一致。

`method`：`GET`、`POST`、`PATCH`、`DELETE`。`handler` 是接口包里的导出函数名，匹配 `^[A-Z][A-Za-z0-9]{0,60}$`。`timeout_ms` 取值 100–10000，默认 3000。

`path_template` 以 `/` 开头，至少一段。每一段是字面量 `^[a-z][a-z0-9_]{0,40}$`，或路径参数 `{name}`，`name` 用同一套编码规则。可以有一段动作后缀，例如 `/orders/{id}:confirm`。模板里禁止 `..`、空段、查询串和完整 URL。同一修订内，方法加模板唯一。

领域导出函数不单独建表。发布检查时从源码扫出来，装进该修订的解释器。

## 4. 草稿与发布

管理接口前缀 `/api/v1/ext-src`，调用方与 v1 结构 API 相同。

```text
PUT    /apps/{appCode}/files/{layer}/{filename}
GET    /apps/{appCode}/files/{layer}/{filename}
DELETE /apps/{appCode}/files/{layer}/{filename}

PUT    /apps/{appCode}/routes
GET    /apps/{appCode}/routes

POST   /apps/{appCode}:check
POST   /apps/{appCode}:publish
GET    /apps/{appCode}/published
```

`PUT` 文件和路由都写在草稿上。没有草稿时，从当前已发布修订复制出一份新草稿；还没有任何修订时创建 `revision = 1` 的空草稿。复制完成后，后续 `PUT` 只改草稿。已发布修订的行不再更新。

`DELETE` 文件只删草稿里的文件。路由 `PUT` 提交整表替换草稿中的路由列表。

`:check` 不切换流量，步骤与发布前半段相同：

1. `go/parser` 解析草稿里的全部文件。
2. 按第 7 节拒绝禁用语法和禁用 import。
3. 在临时解释器里装载领域包、再装载接口包。
4. 每个路由的 `handler` 必须能断言成接口签名。
5. 每个领域包导出的、符合领域签名的函数记入检查结果；不符合签名的导出函数使检查失败。
6. 丢掉临时解释器，不放入运行池。

`:publish` 在检查通过后，同一短事务里把草稿改为 `published`、旧的已发布改为 `retired`。事务提交后，按第 5 节建新的解释器池，并用原子指针换上。换上之前已经取走旧池的请求继续用旧修订，直到请求结束。新请求使用新修订。旧池排空后释放。

检查或装载失败时，已发布修订保持原样，接口返回 422，正文带文件名、行号和 Yaegi 或解析器的错误。

进程启动时读取每个应用 `phase = published` 的修订，预建解释器池。某个应用装载失败则该应用的扩展接口返回 503，平台自身的 `/api/v1/model` 与 `/api/v1/data` 继续服务。

## 5. 解释器池

Yaegi 的一个 `Interpreter` 不能同时执行两次调用。每个已发布修订持有一个池，池大小默认 4，可用配置改为 1–16。池中每个解释器在创建时独立完成：写入虚拟文件系统、`Use` 符号表、`EvalPath` 领域包、`EvalPath` 接口包、断言导出函数。

虚拟文件布局：

```text
src/itbase.app/{appCode}/domain/{filename}
src/itbase.app/{appCode}/api/{filename}
```

一次调用：

1. 从该修订的池中借出一个解释器。池空则等待，最多等该路由的 `timeout_ms`。等不到返回 503。
2. 执行对应函数。宿主在函数返回或 `ctx` 取消后把解释器还回池。
3. 调用发生 panic 时，该解释器不再还回。宿主另起一个补位解释器，从同一份已发布源码重新装载。补位完成前池容量减一。

Yaegi 无法抢占一段不读取 `ctx` 的死循环。借出时间超过 `timeout_ms` 后，宿主取消 `ctx`、结束本次 HTTP 请求，并且同样丢弃该解释器，避免把卡死的实例再借给下一个请求。被丢弃的调用所在 goroutine 会留到那段循环自己结束；因此第 7 节限制源码体积和语法，发布夹具覆盖这条丢弃路径。

`context` 由宿主创建：`WithTimeout(parent, timeout_ms)`。`itb` 的读写在每次数据库往返前尊重取消。

## 6. 新接口如何挂到 HTTP

平台在 GoFrame 上注册一条编译期路由：

```text
ALL /api/v1/ext/{appCode}/{path}
```

`{path}` 承接剩余路径。宿主用已发布修订的路由表做匹配，不把扩展路径注册成可以覆盖 `/api/v1/model` 或 `/api/v1/data` 的路由。

匹配成功后：

1. 解析登录态，得到 `Actor`。未登录返回 401。v1 第 12 节的权限挂点仍包在 `itb.App` 的读写外面；扩展路由本身在 v1.1 只要求已登录，不在路由表上再存一套角色。
2. 路径参数写入 `Request.Params`，查询串写入 `Request.Query`，JSON 对象写入 `Request.Body`。体不是 JSON 对象则 400。`GET` 和 `DELETE` 的体必须为空。
3. 从池中借解释器，调用 `api.{handler}`。
4. 返回 `*itb.Fail` 时使用其中的状态码和 `code`、`message`。返回 `Response` 时使用其 `Status` 与 `Body`。

领域函数也可以不经 HTTP 被平台内部调用，供以后的工作流或管理端试运行使用：

```text
POST /api/v1/domain/{appCode}/{funcName}
```

请求体是 JSON 对象，成为 `Input.Body`。`funcName` 必须是该修订领域包里已断言成功的导出函数。调用同样借池、同样超时、同样把数据端口限制在当前应用。

## 7. 源码限制

单文件源码不超过 64KB，一个修订的源码合计不超过 512KB，一个修订最多 32 个文件、32 条路由。

发布前用标准库 `go/parser` 与 `go/ast` 走查，出现下列情况则检查失败：

- import 路径不是下面之一：`context`、`errors`、`fmt`、`math`、`strconv`、`strings`、`time`、`encoding/json`、`itbase.dev/itb`，以及接口文件对 `itbase.app/{appCode}/domain` 的引用
- `go` 语句
- `select`、`defer` 以外的裸 `go` 调用；`defer` 允许
- `init` 函数
- 类型参数、泛型实例化
- `unsafe`、`reflect`、`import _`
- cgo、`//go:embed`、构建标签

`defer` 允许，用来在领域函数里表达释放之外的本地清理；由于没有拿到文件和连接，清理对象只有内存值。

标准库子集由宿主逐包导出，不转交 `os`、`net`、`database/sql`、`plugin`、`syscall`、`runtime`、`reflect`、`unsafe`。`fmt` 只导出 `Sprintf`、`Errorf`、`Sprint`。

解释器选项保持 Yaegi 默认的安全边界，不打开访问宿主任意内存的开关。

## 8. 与 v1 管线的关系

扩展代码需要新列、新关联时，先调用 v1 结构 API，等字段和关联变为 `active`，再发布引用这些编码的源码。解释器里没有结构 API 客户端。

CEL 继续负责能写成布尔表达式的规则。跨多行写入、需要循环聚合或要返回自定义形状的响应时，写领域函数。领域函数里的每一次 `Create` / `Update` 仍会跑该实体的 CEL。

自定义接口返回的记录形状与 v1 第 10.3 节一致时，直接把 `itb.Record` 放进 `Response.Body`。需要别的形状时，在接口包里组装 `map`。

工作流以后要执行业务动作时，调用已发布的领域函数，不另写一套脚本语言，也不在工作流里打开第二个不受本节限制的解释器。

## 9. 示例

草稿中的领域文件 `domain/order.go`：

```go
package domain

import (
    "context"

    "itbase.dev/itb"
)

func Confirm(ctx context.Context, in itb.Input) (itb.Output, error) {
    app, err := itb.Current(ctx)
    if err != nil {
        return itb.Output{}, err
    }
    id, _ := in.Body["id"].(float64)
    var out itb.Record
    err = app.Tx(ctx, func(tx *itb.App) error {
        rec, err := tx.Update(ctx, "order", uint64(id), itb.Write{
            Values: map[string]any{"status": "confirmed"},
        })
        if err != nil {
            return err
        }
        out = rec
        return nil
    })
    if err != nil {
        return itb.Output{}, err
    }
    return itb.Output{Body: map[string]any{"id": out.ID, "values": out.Values}}, nil
}
```

草稿中的接口文件 `api/order.go`：

```go
package api

import (
    "context"

    "itbase.app/crm/domain"
    "itbase.dev/itb"
)

func ConfirmOrder(ctx context.Context, req itb.Request) (itb.Response, error) {
    out, err := domain.Confirm(ctx, itb.Input{
        Actor: req.Actor,
        Body:  map[string]any{"id": req.Params["id"]},
    })
    if err != nil {
        return itb.Response{}, err
    }
    return itb.Response{Body: out.Body}, nil
}
```

对应草稿路由：`POST` `/orders/{id}:confirm` → `ConfirmOrder`，超时 3000。发布后，客户端调用：

```text
POST /api/v1/ext/crm/orders/41:confirm
```

宿主匹配到该模板，领域函数通过 `tx.Update` 写入。订单上的 CEL 规则失败时，事务回滚，接口得到 422。

JSON 数字进 `map[string]any` 时是 `float64`。领域函数把路径参数转成 `uint64` 时应走 `strconv`，上面的示例为缩短篇幅直接断言。夹具里的正式例子用 `strconv.ParseUint`。

## 10. v1.1 做完的标准

- 不重新编译平台，能够保存草稿、检查、发布一份含领域包和接口包的修订，并立刻用新路由访问到新函数。
- 发布失败时，原已发布修订继续服务。
- 领域函数里的 `Create` / `Update` 与直接调用 `/api/v1/data` 一样触发 CEL；规则失败时 `Tx` 整单回滚。
- 源码 import `os` 或写出 `go` 语句时，`:check` 失败，运行池不变。
- 两个并发请求不会借到同一个解释器。其中一个请求 panic 后，下一个请求仍能完成，池会补回实例。
- 平台启动夹具包含：双包互调、`Tx` 回滚、只读 `GET` 写操作被拒绝、路由不覆盖 `/api/v1/data`。
