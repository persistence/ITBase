# 元数据目录

职责：在应用内登记实体、字段、关联、索引、选项集；规定编码、物理名、逻辑类型和系统字段。结构变更里「只改目录、不跑 DDL」的部分也在本模块完成。

不负责：DDL 执行与任务状态机（见 [结构同步](02-结构同步.md)）；CEL 表达式的编译与求值（见 [规则校验](03-规则校验.md)）；业务行读写（见 [数据读写](04-数据读写.md)）。

依赖：无。其它模块都只认本模块里 `active` 的对象。

结构 API 前缀 `/api/v1/model`。调用方是管理后台和搭建用的 Skill。请求都带应用标识，实体编码在应用内查找。

## 1. 标识与物理名

应用编码、实体编码、字段编码、关联编码、选项编码、规则编码、索引用同一套规则：

```text
^[a-z][a-z0-9_]{0,39}$
```

最长 40 个字符，与目录里的 `VARCHAR(40)` 一致。禁止使用第 4 节列出的系统列名，以及 MySQL 保留字。

物理名只在创建时生成一次，记在目录里：

| 对象 | 物理名 |
|---|---|
| 实体表 | `{appCode}__{entityCode}` |
| 字段列 | 字段编码 |
| 普通索引 | `ix_{entityId}_{indexId}` |
| 全文索引 | `ft_{entityId}_{indexId}` |
| 多对多中间表 | `j_{linkId}` |

表名、列名、索引名的长度必须 `<= 64`。超长则创建接口直接失败，不截断、不哈希。创建实体时检查 `len(appCode) + len(entityCode) + 2 <= 64`。`app_code` 是生成表名时的副本，应用以后改编码也不改表名。

业务表统一 `InnoDB`、`utf8mb4`、`utf8mb4_0900_ai_ci`。这套排序规则不区分大小写：唯一索引里 `PO-1` 与 `po-1` 是同一个键。时间列用 `DATETIME(3)`，由应用传入 UTC。写入路径禁止使用 `NOW()`、`CURRENT_TIMESTAMP` 和会话时区。连接会话固定 `time_zone = '+00:00'`。

同一实体上，字段编码与导航编码共用一个名字空间，落在 `dm_name`。创建字段、关联或系统列时插入；清除时删除。停用只改对象状态，不释放名字。

## 2. 逻辑类型

第一期字段只有下表这些种类。公式、自动编号、树、视图不在这一期。

| kind | scalar_type | MySQL | API JSON | CEL 里的类型 |
|---|---|---|---|---|
| scalar | string | `VARCHAR(n)`，n 默认 255，最大 1000 | 字符串 | string |
| scalar | text | `TEXT` | 字符串 | string |
| scalar | int | `INT` | JSON 数字 | int |
| scalar | bigint | `BIGINT` | 十进制字符串 | string |
| scalar | decimal | `DECIMAL(p,s)`，默认 `(18,4)` | 十进制字符串 | string |
| scalar | bool | `TINYINT(1)` | `true` / `false` | bool |
| scalar | date | `DATE` | `YYYY-MM-DD` | string |
| scalar | datetime | `DATETIME(3)` | UTC RFC3339，毫秒 | string |
| scalar | json | `JSON` | 对象或数组 | 第一期不进入 CEL |
| option | — | `VARCHAR(40)`，存选项编码 | 字符串 | string |
| file | — | `JSON`，文件 id 的字符串数组 | 字符串数组 | 第一期不进入 CEL |
| ref | — | `BIGINT UNSIGNED`，引用列 | 不放在 `values` 里，走关联写入 | 不进入 CEL |

`INT` 的范围在 JSON 安全整数内，所以 `int` 用 JSON 数字。`bigint`、记录 `id`、外键、`rowVersion`、操作者 id 一律用十进制字符串。请求里若用 JSON 数字表达这些值，接口返回 400。`decimal` 同样用字符串，避免二进制浮点。`p` 取值 1–38，`s` 取值 0–p。`string` 的 `n` 取值 1–1000。

选项集在应用内共享。字段只引用选项集，不在字段上复制一份选项。

`ref` 列只出现在「多」的一侧，用来承载多对一或一对一。列编码等于 owner 侧导航编码，这个编码在 `dm_name` 里记为字段名，不再另记一条导航名。一对多没有自己的列，它是对方引用列的反向导航名，只占用目标实体的导航名。多对多没有业务列，两侧导航名都只记为导航名。引用列不建数据库外键。

成员、部门不单设字段种类。需要时建成指向组织模块实体的 `ref`。组织模块尚未建模时，先不在业务表里放裸的成员 id 列。

## 3. 每张业务表固定带上的列

创建实体时由执行器建表。目录事务里同时插入 `origin = system` 的字段行，状态为 `pending`。建表任务 `applied` 后，这些行和实体一起改为 `active`。这些字段不能通过字段 API 修改或删除。

```sql
id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '行主键',
row_version    BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '乐观锁。插入为 1，一次事务最多加 1',
created_at     DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
created_by     BIGINT UNSIGNED NOT NULL COMMENT '创建人用户 id',
updated_at     DATETIME(3)     NOT NULL COMMENT '最后修改时间，UTC',
updated_by     BIGINT UNSIGNED NOT NULL COMMENT '最后修改人用户 id',
deleted_at     DATETIME(3)     NULL COMMENT '软删除时间，UTC。未删除为空',
deleted_token  BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '未删除为 0。软删除后写成该行 id，供唯一索引复用业务键',
PRIMARY KEY (id)
```

`row_version` 在插入时为 1。同一行在一次数据事务里无论改了多少列、外键或成员关系，提交时只加 1。`PATCH` 和 `DELETE` 必须带上读到的版本，不匹配则 409。

`soft_delete = 1` 时，删除把 `deleted_at` 写成当前 UTC 时间，并把 `deleted_token` 写成该行 `id`。未删除行的 `deleted_token` 保持 0。列表默认加 `deleted_token = 0`。

唯一约束一律建成 `(业务列…, deleted_token)`。这样软删除后，同一业务键可以再次使用。实体若关闭软删除，则不建 `deleted_at` 与 `deleted_token`，唯一索引只含业务列，删除改为物理 `DELETE`。第一期建议所有业务实体都开启软删除，创建后再改这个开关会牵涉唯一索引重建，接口不提供该开关的修改。

可空列上的多个 `NULL` 在 MySQL 唯一索引里彼此不相等。唯一约束管不住「多个空值」。需要「最多一个空值」时，把列建成必填。

`created_by` / `updated_by` 来自当前登录用户，请求体里的同名键忽略。

## 4. 系统字段

下列编码保留，不能作为自定义字段或导航编码，并在创建实体的目录事务里写入 `dm_name`：

```text
id, row_version, created_at, created_by, updated_at, updated_by, deleted_at, deleted_token
```

对应的 `dm_field` 行与建表任务同一事务插入，`origin = system`。任务 `applied` 后 `status = active`。任务失败则这些行保持 `failed`，与实体一起处理。数据 API 的 `values` 不接受这些键。读记录时，`id`、`rowVersion` 与审计列放在记录外层，不放进 `values`。

## 5. 目录表

### 5.1 dm_entity

```sql
CREATE TABLE dm_entity (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '实体主键',
  app_id        BIGINT UNSIGNED NOT NULL COMMENT '所属应用',
  app_code      VARCHAR(40)     NOT NULL COMMENT '生成表名时的应用编码副本，之后不随应用编码变化',
  code          VARCHAR(40)     NOT NULL COMMENT '实体编码。应用内唯一，创建后不改',
  title         VARCHAR(80)     NOT NULL COMMENT '显示名',
  table_name    VARCHAR(64)     NOT NULL COMMENT '物理表名，创建时定死',
  title_field   VARCHAR(40)     NULL COMMENT '标题字段编码。须为 active 的 string 或 option，可后补',
  soft_delete   TINYINT(1)      NOT NULL DEFAULT 1 COMMENT '1 软删除，0 物理删除。创建后不可改',
  revision      INT UNSIGNED    NOT NULL DEFAULT 0 COMMENT '结构版本。每次结构任务成功加 1，不是源码修订号',
  status        VARCHAR(16)     NOT NULL COMMENT 'pending、active、failed、archived',
  created_at    DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at    DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_entity_app_code (app_id, code),
  UNIQUE KEY uk_dm_entity_table (table_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '实体目录';
```

`status`：`pending`、`active`、`failed`、`archived`。创建实体时为 `pending`，建表任务 `applied` 后改为 `active`。`revision` 在每次结构任务成功后加 1，表示结构版本，与源码修订不是同一个数。`title_field` 指向一个 `active` 的 `string` 或 `option` 字段，供关联展示使用；可以后补。

数据 API 只读写 `active`。`pending` 和 `failed` 返回 409。`archived` 返回 404。

### 5.2 dm_field

```sql
CREATE TABLE dm_field (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '字段主键',
  entity_id     BIGINT UNSIGNED NOT NULL COMMENT '所属实体',
  code          VARCHAR(40)     NOT NULL COMMENT '字段编码，同时是物理列名。创建后不改',
  title         VARCHAR(80)     NOT NULL COMMENT '显示名',
  kind          VARCHAR(16)     NOT NULL COMMENT 'scalar、option、file、ref',
  scalar_type   VARCHAR(16)     NULL COMMENT 'kind=scalar 时的逻辑类型，其余为空',
  char_length   INT             NULL COMMENT 'string 的长度',
  num_precision INT             NULL COMMENT 'decimal 的精度 p',
  num_scale     INT             NULL COMMENT 'decimal 的标度 s',
  required      TINYINT(1)      NOT NULL DEFAULT 0 COMMENT '1 必填',
  option_set_id BIGINT UNSIGNED NULL COMMENT 'kind=option 时引用的选项集',
  origin        VARCHAR(16)     NOT NULL COMMENT 'system 或 custom',
  status        VARCHAR(16)     NOT NULL COMMENT 'pending、active、failed、retired',
  sort_no       INT             NOT NULL DEFAULT 0 COMMENT '显示顺序',
  created_at    DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at    DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_field_entity_code (entity_id, code),
  KEY idx_dm_field_entity_status (entity_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '字段目录';
```

`kind`：`scalar`、`option`、`file`、`ref`。`origin`：`system`、`custom`。`status`：`pending`、`active`、`failed`、`retired`。

单列唯一不放在本表，统一走 `dm_index`，便于和软删除令牌拼在一起。

`ref` 字段的目标实体记录在 `dm_link`，不在本表重复一份。

### 5.3 dm_name

字段编码和导航编码的唯一性不靠应用层检查单独保证。

```sql
CREATE TABLE dm_name (
  entity_id  BIGINT UNSIGNED NOT NULL COMMENT '所属实体',
  code       VARCHAR(40)     NOT NULL COMMENT '字段编码或导航编码',
  kind       VARCHAR(16)     NOT NULL COMMENT 'field 或 nav',
  ref_id     BIGINT UNSIGNED NOT NULL COMMENT 'kind=field 时为 dm_field.id，kind=nav 时为 dm_link.id',
  PRIMARY KEY (entity_id, code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '实体内字段名与导航名的唯一名字空间';
```

`kind`：`field` 或 `nav`。`ref_id` 指向 `dm_field.id` 或 `dm_link.id`。

| 名字 | kind | 说明 |
|---|---|---|
| 系统列、标量、选项、文件 | `field` | 与 `dm_field.code` 相同 |
| 多对一、一对一的 owner 导航 | `field` | 与引用列是同一个编码，只插一行 |
| 反向导航（一对多、反向一对一） | `nav` | 目标实体上的导航名，不能再占用字段编码 |
| 多对多两侧导航 | `nav` | 两侧都没有引用列 |

自关联允许：`owner_entity_id = target_entity_id`，两个编码都进同一实体的 `dm_name`，因此必须不同。

### 5.4 dm_link

一条 `dm_link` 表示一种关联，同时给出两侧的导航名。

```sql
CREATE TABLE dm_link (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '关联主键',
  app_id             BIGINT UNSIGNED NOT NULL COMMENT '所属应用',
  kind               VARCHAR(16)     NOT NULL COMMENT 'many_to_one、one_to_one、many_to_many',
  owner_entity_id    BIGINT UNSIGNED NOT NULL COMMENT '持有引用列或正向导航的实体',
  owner_field_id     BIGINT UNSIGNED NULL COMMENT '引用列 dm_field.id。多对多为空',
  owner_nav_code     VARCHAR(40)     NOT NULL COMMENT 'owner 侧导航编码。多对一、一对一与引用列编码相同',
  target_entity_id   BIGINT UNSIGNED NOT NULL COMMENT '目标实体',
  target_nav_code    VARCHAR(40)     NOT NULL COMMENT '目标侧反向导航编码',
  junction_table     VARCHAR(64)     NULL COMMENT '多对多中间表名。其余种类为空',
  required           TINYINT(1)      NOT NULL DEFAULT 0 COMMENT '1 表示写入时必须带目标',
  status             VARCHAR(16)     NOT NULL COMMENT 'pending、active、failed、retired',
  created_at         DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at         DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_link_owner_nav (owner_entity_id, owner_nav_code),
  UNIQUE KEY uk_dm_link_target_nav (target_entity_id, target_nav_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '关联。一条记录同时给出两侧导航名';
```

| kind | 引用列放在哪 | owner 侧导航 | target 侧导航 | 数据 API 含义 |
|---|---|---|---|---|
| many_to_one | owner 表的 `owner_field_id` | 多对一，例如订单上的 `customer` | 一对多，例如客户上的 `orders` | `set` 改引用列；在 target 侧 `create` 会插入 owner 行 |
| one_to_one | owner 表的 `owner_field_id`，并加唯一索引 | 一对一 | 反向一对一 | 同上，引用列在未删除行中唯一 |
| many_to_many | `junction_table` | 导航名 | 反向导航名 | `link` / `unlink` 写中间表 |

引用列是普通 `BIGINT UNSIGNED`。目标行是否存在由数据 API 在写入时检查。删除目标行只改目标行本身，引用列保持原值。

写关联时按 `dm_entity.id` 升序对两侧实体 `SELECT … FOR UPDATE`，再插入 `dm_name`。只锁 owner 不够，反向导航落在目标实体的名字空间里。

### 5.5 dm_index 与 dm_index_column

```sql
CREATE TABLE dm_index (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '索引主键',
  entity_id   BIGINT UNSIGNED NOT NULL COMMENT '所属实体',
  code        VARCHAR(40)     NOT NULL COMMENT '索引编码，创建后不改',
  unique_key  TINYINT(1)      NOT NULL COMMENT '1 唯一索引。全文索引固定为 0',
  index_kind  VARCHAR(16)     NOT NULL COMMENT 'btree 或 fulltext。创建后不改',
  index_name  VARCHAR(64)     NOT NULL COMMENT '物理索引名。btree 为 ix_{entityId}_{indexId}，全文为 ft_{entityId}_{indexId}',
  status      VARCHAR(16)     NOT NULL COMMENT 'pending、active、failed',
  created_at  DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at  DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',
  PRIMARY KEY (id),
  UNIQUE KEY uk_dm_index_entity_code (entity_id, code),
  UNIQUE KEY uk_dm_index_name (index_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '索引目录';

CREATE TABLE dm_index_column (
  index_id  BIGINT UNSIGNED NOT NULL COMMENT '所属索引',
  field_id  BIGINT UNSIGNED NOT NULL COMMENT '索引列 dm_field.id',
  seq       INT             NOT NULL COMMENT '列序，从 1 起。MATCH 必须与这个顺序一致',
  PRIMARY KEY (index_id, seq),
  UNIQUE KEY uk_dm_index_column (index_id, field_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT '索引列';
```

`index_kind` 为 `btree` 或 `fulltext`。创建请求省略 `kind` 时记 `btree`。`fulltext` 的 `unique_key` 固定为 0，物理名、列规则和查询见 [全文索引](08-全文索引.md)。

B 树唯一索引在软删除实体上的物理列序是：声明的字段顺序，最后加 `deleted_token`。B 树非唯一索引不加 `deleted_token`。

B 树索引列只能是 `active` 的 `string`、`int`、`bigint`、`decimal`、`bool`、`date`、`datetime`、`option`、`ref`。`text`、`json`、`file` 不参与 B 树索引。列数 1–5。`utf8mb4` 下 InnoDB 二级索引键长上限 3072 字节，单列最多 768 个字符；声明列按最大字节相加超过上限时，创建接口直接失败。超过该键长的 `string`，以及全部 `text`，使用全文索引。

### 5.6 dm_option_set 与 dm_option_item

```sql
  code        VARCHAR(40)     NOT NULL COMMENT '选项集编码，创建后不改',
  title       VARCHAR(80)     NOT NULL COMMENT '显示名',
  created_at  DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at  DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',

CREATE TABLE dm_option_item (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '选项主键',
  set_id      BIGINT UNSIGNED NOT NULL COMMENT '所属选项集',
  code        VARCHAR(40)     NOT NULL COMMENT '选项编码。写入业务列的值，创建后不改',
  title       VARCHAR(80)     NOT NULL COMMENT '显示名',
  sort_no     INT             NOT NULL DEFAULT 0 COMMENT '显示顺序',
  enabled     TINYINT(1)      NOT NULL DEFAULT 1 COMMENT '1 可写入。停用后已有行仍可读，接口不提供物理删除',
  created_at  DATETIME(3)     NOT NULL COMMENT '创建时间，UTC',
  updated_at  DATETIME(3)     NOT NULL COMMENT '更新时间，UTC',

  UNIQUE KEY uk_dm_option_item (set_id, code)

```

停用选项后，新写入不能再使用该编码，已有行仍可读出。删除选项编码会造成历史值无法解释，接口不提供物理删除，只提供停用。

## 6. 结构 API（目录部分）

```text
POST   /apps/{appCode}/entities
PATCH  /apps/{appCode}/entities/{entityCode}
POST   /apps/{appCode}/entities/{entityCode}:archive

POST   /apps/{appCode}/option-sets
POST   /apps/{appCode}/option-sets/{setCode}/items
PATCH  /apps/{appCode}/option-sets/{setCode}/items/{itemCode}

POST   /apps/{appCode}/entities/{entityCode}/fields
PATCH  /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}
POST   /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}:retire
POST   /apps/{appCode}/entities/{entityCode}/fields/{fieldCode}:purge

POST   /apps/{appCode}/entities/{entityCode}/links
POST   /apps/{appCode}/entities/{entityCode}/links/{navCode}:retire

POST   /apps/{appCode}/entities/{entityCode}/indexes
DELETE /apps/{appCode}/entities/{entityCode}/indexes/{indexCode}

GET    /apps/{appCode}/entities/{entityCode}
GET    /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}
POST   /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}:retry
POST   /apps/{appCode}/entities/{entityCode}/schema-tasks/{taskId}:abandon
```

规则接口见 [规则校验](03-规则校验.md)。任务如何执行、何时返回 202，见 [结构同步](02-结构同步.md)。`GET …/validate-spec` 见 [规则校验](03-规则校验.md)。

需要 DDL 的操作：本模块在短事务里写入目录（对象 `status = pending`）并插入结构任务，提交后交给结构同步模块执行。同一实体只要还有 `pending`、`running`、`blocked` 或未处理的 `failed` 任务，就拒绝下一次结构变更。结构 API 用 `SELECT … FOR UPDATE` 锁住相关 `dm_entity` 行来保证这一点。关联锁两侧，锁的顺序是实体 id 升序。

归档之后只允许读取目录。结构变更接口返回 409。

### 6.1 允许的结构改动

创建实体时一次登记系统列和系统字段，并插入一条 `create_table` 任务。此时还没有自定义字段。实体保持 `pending`，直到该任务 `applied`。

| 操作 | 目录 | DDL |
|---|---|---|
| 改显示名、排序、标题字段 | 直接更新 | 无 |
| 加字段 | `pending` → `active` | `ADD COLUMN`，新列先可空 |
| 放宽 `VARCHAR` 长度 | 更新 `char_length` | `MODIFY COLUMN` |
| 增大 `DECIMAL` 的精度且标度不变或变大 | 更新精度 | `MODIFY COLUMN` |
| 把可空改为必填 | 先查该列不存在 `NULL`，并核对实例心跳，通过后更新 | `MODIFY COLUMN … NOT NULL` |
| 把必填改为可空 | 更新 | `MODIFY COLUMN … NULL` |
| 停用字段 | `retired` | 无 |
| 清除已停用字段 | 删除目录行和 `dm_name` | `DROP COLUMN` |
| 加索引、删索引 | 对应任务 | `ADD INDEX` / `DROP INDEX` |
| 加关联 | 见 6.2 | 见 6.2 |

把可空改为必填时，请求体带 `minRevision`（源码修订号，整数）。执行条件见 [结构同步](02-结构同步.md) 与 [多实例归属](09-多实例归属.md)：该列没有 `NULL`；若应用已有 `published` 修订，则每个新鲜的 `api` 心跳都已经装上大于等于 `minRevision` 的修订。心跳只说明各进程的解释器版本，不说明浏览器和外部调用方已经会传这个字段。因此仍要求 `confirm=true`。应用从未发布源码时，不检查 `minRevision`，只检查 `NULL` 和 `confirm=true`。

下列改动接口直接拒绝：

- 修改任意编码、物理表名、物理列名
- 修改 `kind` 或 `scalar_type`
- 缩短字符串、减小数值精度、减小标度
- 更换关联的目标实体
- 删除仍被关联引用的字段
- 清除仍出现在 `dm_index_column` 中的字段
- 停用或清除仍被启用规则的 `fields_json` 或 `reads_json` 引用的字段或导航
- 归档仍被其他 `active` 关联指向的实体
- 修改 `soft_delete`

停用后的字段仍留在表上，历史行还在，`dm_name` 仍占用该编码。`purge` 要求当前状态是 `retired`，并且请求带 `confirm=true`。`purge` 的 `reverse_ddl` 为空，数据不可自动找回。

归档实体只改 `status = archived`，不删表。数据 API 拒绝读写。归档前要求没有指向它的 `active` 关联，并且该实体没有未完成的结构任务。

数据 API 只认 `active`。`pending`、`failed`、`retired` 都不会出现在写入和校验说明里。

### 6.2 新增关联时目录里有什么

新增多对一 `order.customer → customer.orders`。目录事务按实体 id 顺序锁住订单和客户两行：

1. 在订单上插入 `kind = ref` 的字段，编码等于 `owner_nav_code`（`customer`），`status = pending`。`dm_name` 插入一行 `kind = field`。
2. 插入 `dm_link`，`status = pending`。在客户上插入 `dm_name`，`kind = nav`，编码为 `orders`。
3. 插入一条 `add_column` 任务，`status = pending`。不建数据库外键。
4. 列任务 `applied` 后，字段与关联改为 `active`。

一对一的前两步相同。同一次目录事务里再插入唯一索引任务，`status = blocked`，`depends_on` 指向列任务。列是该引用列加 `deleted_token`。列任务 `applied` 后，执行器把索引任务放行为 `pending` 并执行。索引任务 `applied` 后，字段与关联才改为 `active`。索引任务仍停在 `blocked` 或 `failed` 时，数据 API 看不见这条关联。

新增多对多只插入 `dm_link`、两侧 `dm_name`（都是 `nav`）和一条 `create_junction` 任务。中间表形态见 [结构同步](02-结构同步.md)。

### 6.3 失败之后

`retry` 只接受 `failed` 任务，行为见结构同步。

`:abandon` 只接受 `failed` 任务，并且 `information_schema` 必须表明 `forward_ddl` 没有生效。此时删除该任务带起来的 `pending` / `failed` 目录行和 `dm_name`，并删除仍为 `blocked` 的后续任务。列或索引已经变成目标定义时，放弃返回 409，只能 `retry` 把目录收成 `active`。

## 7. 本模块完成标准

- 能创建应用内实体，登记第 2 节的字段种类，登记多对一、一对一、一对多导航和多对多，登记唯一索引、普通索引和全文索引。
- 编码最长 40；表名超长被拒绝；系统字段、选项集共享、`dm_name` 按本文执行。引用列与 owner 导航共用一个字段名。
- 需要 DDL 的变更能在一次短事务里插入 `pending` 对象、`pending` 任务和必要的 `blocked` 后续任务，并锁住相关实体。
- 一对一不会出现「列已经加上、目录里却没有索引任务」的窗口。
- 启用中的规则仍引用某字段或导航时，停用和清除被拒绝。
